# Requirements Document

## Introduction

This document specifies the Kanban Task Management application (Version V12). It is a role-based web app with a Flask REST API backend and a mobile-first Next.js frontend. Teams run day-to-day work on boards, columns, and cards, and supervisors and managers oversee progress through analytics without opening every board.

The requirements translate decisions already recorded in `specs/project-brief.md` and the steering documents in `.kiro/steering/`. V10 revises V9 and changes product behaviour in six areas, each recorded as a decision (K to P): Guests read a Board only through a Share_Link (Decision K, Requirement 18); every signed-in page carries an App_Header with a User_Menu that holds Profile and Log out (Decision L, Requirement 19); a User has a separate Username and Email in place of `login_identifier` (Decision M); login takes one `identifier` field (Decision N); a Rate_Limiter protects login and the availability check (Decision O, Requirement 20; registration limiting is deferred by Decision Q); and every page of the signed-in application is a Protected_Route (Decision P). V10 also updates the V9 Playwright criteria to the new login form, the header sign-out, the defined route guard, and the rate-limit case. V9 had added only end-to-end test specifications for sign-in and sign-out (Requirement 1, criteria 19 to 38; Requirement 15, criteria 10 to 15). V8 revised V7 and added no scope beyond the decisions in the Decisions Log. Twenty-eight decisions that resolved gaps in the brief are recorded there: Decisions 1 to 5 (carried from V1), Decisions A to D (carried from V2), Decision E (carried from V4: the Backend uses flask-smorest with marshmallow schemas and a generated OpenAPI document; its numeric `status` rule is superseded by Decision G), Decision F (carried from V5: models declare SQLAlchemy relationships only for real cross-table reads, repositories load related rows explicitly, and serialization belongs to marshmallow schemas), Decision G (carried from V6: the Envelope `status` is a boolean, the message text appears once at the top level, and validation errors carry `error.details`), Decision H (carried from V7: the Frontend is styled with Tailwind CSS and shadcn/ui, themed from the design tokens, and the shared `Base*` components wrap shadcn/ui primitives), Decision J (new in V8: the Inbox and the activity feeds are paged with a `limit` and a `before` cursor; every other list stays unpaged), Decision I (new in V8: the board and the Card modal follow a Trello-style interaction model, Cards move by drag-and-drop only, the font is Inter, and the application is named RevoTask), Decisions K to P (new in V10, listed above), and Decisions Q to T (round 2 within V10: registration rate limiting deferred, avatar upload, the Email shown to staff in the member search and the assignee popover, and the invalid-Token redirect; they amend Decisions L, M, O, and P), and Decisions U to W (round 3 within V10: the avatar routes under `/api/users` and avatars in Comments, Board member lists, candidates, and Card assignees; a local-development reset migration in place of the legacy-account backfill; and a change-password rate limit with a minimum candidate-search length; they amend Decisions M, O, R, and S). Criteria affected by a decision carry an inline label such as "(Decision A)". V11 adds Decision X and Requirement 21 (branding): the RevoTask logo and favicon supplied by the product owner replace the placeholder mark; V11 changes no API, data model, or permission. V12 adds Decisions Y to AF and Requirements 22 to 29: every Board is private and visible only to its owner, its BoardMembers, Managers, and Admins (Decision Y, Requirement 22, reversing Decision A and the Board `visibility` column); the V10 Share_Link becomes the Public_Link, managed only by a Manager or an Admin and read-only for everyone (Decision Z, Requirement 23); a new Invite_Link and BoardJoinRequest flow lets Members and Supervisors ask to join, and only a Manager or an Admin approves (Decision AA, Requirement 24); the Card modal saves every change by itself and loses the Save changes button (Decision AB, Requirement 25, superseding the draft model of Decision I); an author can delete their own Comments and an Attachment removal asks in a modal (Decision AC, Requirement 26); a Member ticks Subtasks on assigned Cards and Card progress is derived from Subtasks (Decision AD, Requirement 27); Inbox rows navigate to their Card or Board and three Notification types are added (Decision AE, Requirement 28); and the Profile page uses a two-column layout on wide screens (Decision AF, Requirement 29). V12 also adds V12 end-to-end criteria to the E2E_Auth_Suite (Requirement 1, criteria 65 to 72) and tests (Requirement 15, criteria 29 to 35). V11 branding (Decision X, Requirement 21) is unchanged.

Out of scope: Google OAuth login (post-MVP, added only after username-or-email and password auth is verified end-to-end), server-side token revocation (deferred past MVP; rate limiting was deferred in V2 and is in scope from V10 for login, the availability check, and change-password, Requirement 20 and Decision W; registration stays unlimited, Decision Q), custom per-board workflow templates beyond the five default columns, and subtasks with their own assignee or date. Stretch features (card `progress` meter, `views_count`, decorative Overview/Notes/Questions tabs) are covered in Requirement 16 and are built only after all other requirements work end-to-end.

This feature requires these data-model additions beyond the original `data-model.md` steering: a nullable `Board.owner_id` (Decision 1), a `BoardMember` entity (Decision A), a nullable unique `Board.share_token` (Decision K), a unique case-insensitive `username` and `email` on User in place of the single `login_identifier` column that Decision C introduced and Decision M removes, a `rate_limit_attempts` table (Decision O), and an `avatar_path` column on User in place of the free-text `avatar_url` column (Decision R). V12 removes `Board.visibility` and adds a nullable unique `Board.invite_token`, a `BoardJoinRequest` entity, and on Notification a nullable `board_id`, `actor_id`, and `join_request_id`, a nullable `card_id`, three new types, and partial unique indexes (Decisions Y, AA, and AE); `Card.progress` becomes a computed field and is never stored (Decision AD).

V14 (draft, not implemented) adds production deployment: Decisions AJ to AN and Requirements 33 to 37. Decision AN is approved; the server type (Open Question 31) is open.

## Glossary

- **System**: The Kanban Task Management application, consisting of the Backend and the Frontend.
- **Backend**: The Flask REST API, organized as one blueprint per domain, each layered `routes.py → service.py → repository.py → schema.py`.
- **Frontend**: The mobile-first Next.js (App Router, TypeScript) application.
- **Design_Tokens**: The visual reference's CSS custom properties (`--brand`, `--surface-*`, `--ink*`, `--space-*`, `--radius-*`, `--shadow-*`, `--ring`, the `--label-*` pairs) defined once in `frontend/styles/tokens.css`. They are the only source of colors, spacing, radii, and shadows.
- **shadcn/ui**: Accessible UI primitives (built on Radix UI) copied into `frontend/components/ui/` and styled with Tailwind CSS utilities. Only the shared `Base*` components import them.
- **Guest**: A visitor without an account or Token. Can open a Board only through a Public_Link (Decisions K and Z) and sees its columns and cards read-only, never its comments or activity. A Guest cannot list or browse Boards, and can open an Invite_Link page only after signing in (Decision AA).
- **Member**: A signed-in user with the member role.
- **Supervisor**: A signed-in user with the supervisor role. Includes everything a Member can do.
- **Manager**: A signed-in user with the manager role. Includes everything a Supervisor can do.
- **Admin**: A signed-in user with the admin role, a separate administrative track and not a superset of Manager (see Requirement 2 and Decision B).
- **Card_Creator**: A Supervisor, Manager, or Admin. Card creation additionally requires Board_Access to the target Board.
- **login_identifier**: The single unique string column on User that Decision C introduced. Removed in V10 (Decision M); it survives only as a historical term in the V2 to V9 snapshots and in the downgrade of the migration.
- **Username**: The User's unique, case-insensitive handle, 3 to 30 characters from `a-z`, `0-9`, `_`, and `.`, stored in lowercase (Decision M).
- **Email**: The User's unique, case-insensitive email address, valid format, at most 255 characters, stored in lowercase. Required on every account: the V10 migration resets local development data, so no account lacks one (Decisions M and V).
- **Identifier**: The single login form value, either a Username or an Email, sent as the request field `identifier` (Decision N). It is treated as an Email only when it contains `@`.
- **Board**: A project container holding Columns, Cards, and Categories. Every Board is private (Decision Y): it has no `visibility`. It has a nullable `owner_id`, a nullable `share_token` (the Public_Link), and a nullable `invite_token` (the Invite_Link).
- **Share_Token**: The random, unguessable, unique string stored in `Board.share_token` (at least 256 bits from a cryptographically secure source). A null value means the Public_Link is off. The column and the name are unchanged in V12 (Decisions K and Z).
- **Public_Link**: The URL `/shared/{token}` built from a Board's Share_Token (the V10 Share_Link, renamed in V12; "Share_Link" in older text means the same thing). Opens the Shared_View for anyone, signed in or not, and is created, regenerated, and disabled only by a Manager or an Admin (Decision Z).
- **Shared_View**: The read-only Frontend view at `/shared/{token}` of a Board's Columns, Cards, Card details, Categories, and Attachment links, without Comments, Activity, Inbox, or any write control, shown to every visitor of a Public_Link who does not already have Board_Access (Decisions K and Z).
- **Board_Owner**: The Supervisor referenced by a Board's `owner_id`. Sees the Board, edits it as a Supervisor with Board_Staff_Access, manages the Invite_Link, and sees pending Join_Requests but does not decide them (Decisions Y and AA).
- **Board_Member**: A join record `(board_id, user_id)` (stored as `BoardMember`), unique per pair, that attaches a Member or a Supervisor to a Board beyond the Board's `owner_id`. A Manager or an Admin is never a Board_Member (Decision Y). Created by a Manager or an Admin directly, or by an approved Join_Request.
- **Board_Access**: A signed-in user has Board_Access to a non-soft-deleted Board exactly when the user is its Board_Owner, a Board_Member, a Manager, or an Admin (Decision Y). Every other signed-in user gets HTTP 403 and a Guest gets HTTP 401. A Public_Link grants only the Shared_View of Requirement 23, and an Invite_Link grants nothing but the right to ask. Card, Comment, Attachment, Activity_Log, and Category access resolves through the owning Board's Board_Access.
- **Board_Staff_Access**: Write access to a Board's content. A user has Board_Staff_Access when the user is a Manager, an Admin, or a Supervisor who is the Board's Board_Owner or a Board_Member. A Member never has it; a Member's writes are limited to the Assigned_Member rules (Decision 2).
- **Invite_Link**: The URL `/invite/{token}` built from a Board's `invite_token`. It lets a signed-in Member or Supervisor send a Join_Request and grants no access by itself. Generated, regenerated, and disabled by the Board_Owner, a Manager, or an Admin (Decision AA).
- **Join_Request**: A `BoardJoinRequest` row `(id, board_id, user_id, status, decided_by, created_at, updated_at)` with status `pending`, `approved`, or `rejected`. At most one pending row exists per `(board_id, user_id)`. Only a Manager or an Admin decides it (Decision AA).
- **Auto_Save**: The Card modal behaviour of Decision AB: each field, Subtask, and Attachment change is sent by its own request when the user commits it, with a visible Saving, Saved, or error state per field, and no Save changes button.
- **Derived_Progress**: The Card's `progress` integer from 0 to 10 computed from its Subtasks (`done` of `total`), null when there are none, never stored or edited (Decision AD).
- **Column**: An ordered list within a Board that contains Cards.
- **Default_Columns**: The five Columns `Todo`, `In Progress`, `Review`, `Revision`, `Done`, in that order, seeded on every new Board.
- **Card**: A unit of work with a title, description, priority, optional start and end dates, optional Category, optional assignee, Subtasks, and Attachments.
- **Assigned_Member**: The user referenced by a Card's `assignee_id`.
- **Priority**: A Card attribute that is exactly one of `high`, `medium`, or `low`.
- **Subtask**: A checklist item of a Card with a title, `is_done` flag, and Float `order`. Has no assignee and no dates.
- **Attachment**: A link (`url`) or an uploaded file (`file_path` and `mime_type`) belonging to a Card. Never has both empty.
- **Signed_File_URL**: A time-limited, signature-bearing URL for an uploaded Attachment file or an Avatar_Image, valid for 15 minutes.
- **Category**: A per-Board label with a name and nullable color, shown as a filter chip.
- **Comment**: A message on a Card. A top-level Comment has a null `parent_id`. A Reply has a non-null `parent_id`.
- **Reply**: A Comment whose `parent_id` references a top-level Comment.
- **Priority_Comment**: A Comment with `is_priority` set to true.
- **Reply_Count**: The denormalized `reply_count` integer on a top-level Comment.
- **Activity_Log**: The append-only `ActivityLog` table recording state-changing actions.
- **Notification**: A server-created record targeting one user, of type `assigned`, `deadline`, `board_join_requested`, `board_added`, or `board_join_rejected` (Decision AE).
- **Inbox**: The side panel listing the signed-in user's Notifications. Each row is a link to the Card or Board it is about (Decision AE).
- **Side_Panel**: The right-side sliding panel shared by Inbox and Activity.
- **Sidebar**: The left navigation holding brand, nav (including Inbox, Activity, and Categories where permitted), the Boards list, and team members. It holds no profile entry and no Log out item (Decision L).
- **App_Header**: The persistent top bar of every Protected_Route page: the Sidebar toggle below 960 pixels, the page context (on a Board, the name, the "Public link" button for a Manager or an Admin, and the "Invite" button for the Board_Owner, a Manager, or an Admin; there is no visibility icon), the Inbox bell, and the User_Menu trigger (Decision L).
- **User_Menu**: The menu opened from the user icon in the App_Header, holding Profile above Log out (Decision L).
- **Profile_Page**: The Protected_Route `/profile` where the signed-in user edits full name and avatar, sees Username and Email, and changes the password (Decision L).
- **Avatar_Image**: The PNG, JPEG, or WebP picture a user uploads on the Profile_Page, at most 2 MB, stored under a generated file name (Decision R).
- **Avatar_URL**: The value of `avatar_url` in a `user` payload, and of `author_avatar_url`, `avatar_url`, and `assignee_avatar_url` in the Comment, Board member, candidate, and Card payloads of Decision U: a Signed_File_URL for the Avatar_Image, or null when the user has none (Decisions R and U).
- **Initials_Avatar**: The fallback avatar that shows the initials of the user's full name when there is no Avatar_URL or the image fails to load (Decision R). The initials are the first letter of each of the first two words of `full_name`, upper-cased; a one-word name gives one letter and a blank name gives `?` (Decision U).
- **Analytics_Summary**: A pre-aggregated payload of counts, deltas, and overdue totals for a Board.
- **Overdue_Card**: A non-soft-deleted Card whose `end_date` is before today and whose Column is not `Done`.
- **Envelope**: The response shape `{ "status": true, "message": string, "data": payload }` for success and `{ "status": false, "message": string, "error": { "code": string, "details"?: object } }` for failure, where `status` is a boolean that is true exactly when the HTTP status is 2xx, `message` is a non-empty string stated once at the top level, and `error` has no `message` field (Decision G).
- **flask-smorest**: The Flask extension through which every blueprint declares request, query, and response marshmallow schemas and from which the OpenAPI 3 document is generated.
- **Soft_Delete**: Setting `deleted_at` on a row instead of removing the row.
- **Token**: The JWT returned by register and login, identifying the acting user and role, with a fixed 24-hour expiry.
- **Rate_Limiter**: The Backend component that counts attempts in the `rate_limit_attempts` Postgres table and blocks further attempts with HTTP 429 `RATE_LIMITED` (Decision O).
- **Rate_Limit_Window**: The sliding period, 900 seconds by default, over which the Rate_Limiter counts attempts (Decision O).
- **Client_IP**: The client address the Rate_Limiter keys on: the connection's remote address, or the address from `X-Forwarded-For` only through the number of trusted proxies configured in `TRUSTED_PROXY_COUNT` (Decision O).
- **APP_TIMEZONE**: The environment variable holding the application's configured server timezone.
- **E2E_Auth_Suite**: The Playwright specs `frontend/tests/e2e/auth/signin.spec.ts` and `frontend/tests/e2e/auth/signout.spec.ts`, which test sign-in and sign-out against the deployed URL (V9).
- **Test_Account**: A seeded, existing user whose Username or Email and password are supplied to the E2E_Auth_Suite through the environment variables `E2E_USER_IDENTIFIER` and `E2E_USER_PASSWORD` (the variable names are unchanged from V9). The suite assumes a Member account and never creates, edits, or deletes accounts (V9). The suite makes at most one failed login attempt against this account per run (AUTH-E2E-SI-06), far below the lockout threshold, and each successful sign-in resets the pair counter. (V12: the Test_Account `member` is a Board_Member of a seeded Board that has a Card assigned to it, so the V12 criteria 69 and 70 have something to open; the suite still never creates or changes data.)
- **Throwaway_Identifier**: A Username-shaped value generated per test run (`e2e-rl-` plus random lowercase characters) that belongs to no account. The rate-limit test (AUTH-E2E-SI-11) fails logins against it, so the Test_Account is never locked and no account is created (V10; see Decision O).
- **Auth_Page_Object**: The Page Object class `AuthPage` in `frontend/tests/e2e/auth/pages/AuthPage.ts` that holds every locator and action of the login page and the Sign_Out_Control, so the specs contain no raw selectors (V9).
- **User_Menu_Trigger**: The App_Header button with the accessible name "User menu". It is visible exactly while a user is signed in, so the E2E_Auth_Suite uses it as the signed-in indicator (V10).
- **Sign_Out_Control**: The "Log out" menu item of the User_Menu. It is the only sign-out control in the Frontend (Decision L, resolving Open Question 6).
- **Session_Cookie**: The browser cookie `kanban_token` that holds the Token (`lib/session.ts`). A signed-out browser has no such cookie.
- **Generic_Login_Error**: The form-level message "Invalid credentials" that the Backend returns for both an unknown Identifier and a wrong password (`auth_service.login`).
- **Protected_Route**: A Frontend page that requires a Session_Cookie and redirects a visitor without one to `/login`. Every page under the `(app)` route group is one: `/boards`, `/boards/{id}` and its sub-pages, `/profile`, `/admin/users`, and `/invite/{token}` (Decision P, resolving Open Question 5; `/invite/{token}` added in V12, Decision AA). `/login`, `/register`, and `/shared/{token}` are not.
- **Safe_Return_Path**: The value of the `next` query parameter on `/login` when it is a path and query that starts with a single `/`, does not start with `//` or `/\`, has no control character, has at most 512 characters, and starts with `/boards`, `/profile`, `/admin`, or `/invite/` (V12, Decision AA); any other value is ignored (Decision T).
- **Brand_Assets**: The three files the product owner supplied in V11: `favicon.ico`, `logo-revo.svg`, and `logo-text-revo.svg`. After the move: `frontend/app/favicon.ico`, `frontend/public/brand/logo-revo.svg`, and `frontend/public/brand/logo-text-revo.svg`.
- **Logo_Mark**: `logo-revo.svg`, the square mark, `viewBox` 480 by 480.
- **Logo_Full**: `logo-text-revo.svg`, the mark with the "RevoTask" wordmark, `viewBox` 540 by 165.
- **BrandLogo**: The only Frontend component that renders a Logo_Mark or Logo_Full (`components/shared/BrandLogo.tsx`), with the variants `mark` and `full`. Feature code uses it and never writes its own `<img>` or `next/image` for the logo.
- **Embedded_Raster**: The base64 PNG that each Brand_Assets SVG file wraps inside an `<svg>` element. Measured in V11: 640 by 640 pixels in `logo-revo.svg` and 720 by 220 pixels in `logo-text-revo.svg`, 8-bit RGB with no alpha channel and no transparency chunk, so each logo has an opaque background. The `viewBox` (480 and 540 wide) is the size at which the raster is shown at about 1.33 device pixels per CSS pixel.
- **Favicon_File**: `frontend/app/favicon.ico`, a Windows icon file with three images (16, 32, and 48 pixels square, 32 bits per pixel), served by the Next.js file convention.

3. **Decision A interpretation (OBSOLETE in V12: Decision Y removes public Boards; see Requirement 22):** Public Boards stay readable by every signed-in user. Decision K restates this and removes only the Guest half.

## Requirements

### Requirement 1: Authentication and Accounts

**User Story:** As a visitor, I want to register and sign in with an email or username and password, so that I can access boards according to my role.

#### Acceptance Criteria

1. WHEN a visitor submits a registration with full name, Username, Email, and password, THE Backend SHALL create a user account with a hashed password and return HTTP 201 with `{ "status": true, "message": "User registered", "data": { "user": { id, full_name, username, email, avatar_url }, "token": "..." } }` (Decisions G, M, and N; reworded in V10).
2. WHEN a registered user submits a valid `identifier` (a Username or an Email) and password to login, THE Backend SHALL return the same `user` and `token` shape as registration, matching the identifier case-insensitively (Decisions M and N; reworded in V10).
3. IF the `identifier` matches no account or the password is wrong, THEN THE Backend SHALL return HTTP 401 with the same error Envelope and the same message in both cases (Decision N; reworded in V10).
4. IF a registration uses a Username or an Email that already exists when compared case-insensitively, THEN THE Backend SHALL return HTTP 409 with the code `CONFLICT` and an `error.details` object that names each duplicate field (`username`, `email`, or both) with a list of message strings (Decisions M and O; reworded in V10).
5. IF a registration omits full name, Username, Email, or password, or a field fails the format rules of criteria 47 and 48, THEN THE Backend SHALL return HTTP 400 with the code `VALIDATION_ERROR` and an `error.details` entry for each failing field (Decision M; reworded in V10).
6. THE Backend SHALL store the user's Avatar_Image reference as a nullable `avatar_path` and SHALL expose it as `avatar_url` in the `user` payload and in the payloads of criterion 34 of Requirement 19 (Decisions R and U; reworded in V10 rounds 2 and 3).
7. WHEN an Admin creates, edits, or assigns a role to a user account, THE Backend SHALL apply the change and record it in the Activity_Log.
8. IF an authenticated user who is not an Admin requests user account management, THEN THE Backend SHALL return HTTP 403, or HTTP 401 when no Token is present.
9. THE Frontend SHALL present the login and register pages as a split-panel layout with a brand panel beside an elevated rounded form card on desktop widths.
10. WHILE the viewport is at mobile width, THE Frontend SHALL hide the brand panel on the login and register pages and show only the form.
11. THE System SHALL exclude Google OAuth login until Username-or-Email and password authentication is verified end-to-end.
12. IF a registration password is shorter than 8 characters, THEN THE Backend SHALL return HTTP 400 with the code `VALIDATION_ERROR`.
13. THE Backend SHALL hash passwords with bcrypt or argon2.
14. WHEN the Backend issues a Token, THE Backend SHALL set a fixed expiry of 24 hours and keep no server-side revocation list.
15. WHEN a user calls `POST /api/auth/logout`, THE Backend SHALL return HTTP 200 with `{ "status": true, "message": "Logged out", "data": null }` (Decision G).
16. WHEN a user logs out, THE Frontend SHALL discard the stored Token, and the issued Token SHALL remain valid until its expiry.
17. [Withdrawn in V10, Decision M] The provisional "no format validation" rule for `login_identifier` no longer applies; criteria 47 and 48 define the formats.
18. [Superseded in V10, Decision O] Rate limiting is no longer deferred; Requirement 20 defines it.

The criteria below specify the Playwright tests of the E2E_Auth_Suite (V9, updated in V10 to the new login form, the header sign-out, the route guard, and the rate limit). They add no product behaviour: each one verifies behaviour specified in criteria 1.2, 1.3, 1.5, 1.9, 1.10, 1.15, 1.16, 1.44 to 1.46, 1.51, Requirements 13, 19, and 20, and Decisions L, N, O, and P. No criterion is pending in V10. Assumptions: the Test_Account exists and is a Member; the specs run against the deployed Frontend and Backend; the login form posts through `lib/api.ts`; each test starts in a fresh browser context with no Session_Cookie; the suite shows "signed in" by the User_Menu_Trigger. Each criterion has a stable ID, and the matching test title begins with that ID.

### Requirement 2: Roles and Permissions

**User Story:** As a system owner, I want strictly layered roles enforced on the server, so that each user can reach only the actions their role allows.

Note (Decision B): Admin is a separate administration track and is deliberately not a superset of Manager. The Admin exclusions in criteria 5 and in Requirement 10 criterion 4 are intentional and must not be changed as a "fix".

#### Acceptance Criteria

1. THE Backend SHALL support exactly five roles: guest, member, supervisor, manager, and admin.
2. THE Backend SHALL treat Manager permissions as a superset of Supervisor permissions, Supervisor permissions as a superset of Member permissions, and Member view access as a superset of Guest view access.
3. THE Backend SHALL treat Admin as a separate administration track with the permissions listed in criteria 4 to 6.
4. THE Backend SHALL permit an Admin to view all Boards, Cards, Comments, and Activity_Log entries, manage user accounts, create and assign Boards, archive and Soft_Delete Boards, set Board visibility, manage Categories, and move and edit any Card (Decision 5). 7. WHEN any mutating endpoint is called, THE Backend SHALL determine the acting role from the Token and ignore any role value in the request body.
8. IF a mutating request has no valid Token, THEN THE Backend SHALL return HTTP 401 with an error Envelope.
9. IF an authenticated user calls a mutating endpoint that the user's role or Board_Access does not permit, THEN THE Backend SHALL return HTTP 403 with an error Envelope.
10. THE Backend SHALL re-validate the caller's role on 100 percent of mutating endpoints.

### Requirement 5: Drag-and-Drop Card Movement

**User Story:** As a team member, I want to drag cards between columns, so that a card's new position persists after a page refresh.

#### Acceptance Criteria

2. WHEN a user drops a Card, THE Frontend SHALL call `PATCH /api/cards/{id}/move` with the target Column and computed Float `order` once, on drop, and reconcile local state with the response.
3. WHEN a drag is in progress, THE Frontend SHALL insert a placeholder at the drop target and animate sibling Cards into place with a FLIP transform.
4. WHEN a Member with Board_Access moves a Card assigned to that Member, THE Backend SHALL apply the move (Decisions 2 and A).
5. IF a Member moves a Card whose `assignee_id` is not that Member, THEN THE Backend SHALL return HTTP 403 (Decision 2).

9. WHEN a page is refreshed after a successful move, THE Frontend SHALL render the Card in the moved position.
10. WHEN a user drops a Card at the first position of a Column, THE Backend SHALL set the Card's `order` to `min_order - 1`, WHEN at the last position, to `max_order + 1`, and WHEN into an empty Column, to 1.0.

### Requirement 13: API Conventions and Data Integrity

**User Story:** As a frontend developer, I want one predictable API shape and consistent data rules, so that the client has a single place to unwrap responses and errors.

#### Acceptance Criteria

1. THE Backend SHALL serve all endpoints under `/api/...` without a version segment.
2. WHEN a request succeeds, THE Backend SHALL return `{ "status": true, "message": <non-empty string>, "data": <payload> }` with the payload as an object, a list, or null, using a short descriptive `message` for each mutating endpoint (for example "Card moved") and "OK" for reads (Decision G).
3. IF a request fails, THEN THE Backend SHALL return `{ "status": false, "message": <non-empty string>, "error": { "code": string, "details"?: object } }` with the matching HTTP status of 400, 401, 403, 404, 405, 409, 429, or 500, stating the message text only at the top level and including no `message` field in `error`, and with `error.details` present only for `VALIDATION_ERROR`, for the `CONFLICT` of a registration (per field, criterion 4 of Requirement 1), and for `RATE_LIMITED` (`retry_after`) (Decisions G and O; amended in V10).
4. THE Backend SHALL return the Envelope shape, including `status` and `message`, on every response except the Swagger UI HTML page, the raw OpenAPI document, and the successful file bytes of the signed file route; error responses of the signed file route SHALL still use the Envelope (Decision G).
5. THE Backend SHALL use a UUID primary key on every entity and include `created_at` and `updated_at` on every entity.
6. THE Backend SHALL include `deleted_at` and `archived_at` on Board and Card.
7. THE Backend SHALL access the database only through each blueprint's own `repository.py`.
8. THE Backend SHALL read CORS origins from an environment variable allow-list and never use the wildcard `*`.
9. THE System SHALL provide a `.env.example` for the Backend and the Frontend and commit no real `.env` file.
10. IF a request carries no Token on an endpoint that requires one, THEN THE Backend SHALL return HTTP 401, and IF a valid Token lacks the required role or Board_Access, THEN THE Backend SHALL return HTTP 403, except `POST /api/auth/register`, `POST /api/auth/login`, `GET /api/auth/availability`, the shared routes of Requirement 18, and the signed file routes of Attachments and avatars (Decisions D and R), which take a signature in place of a Token (Decision K; reworded in V10, the earlier exception for Guests reading public Boards is removed).
11. THE Backend SHALL set the Envelope `status` to true when the HTTP status is 2xx and to false otherwise, on every Envelope response, including 401, 403, 404, 405, 409, 429, and 500 responses and the errors of the signed file route, with the exceptions of the Swagger UI HTML page, the raw OpenAPI document, and the successful file bytes of the signed file route, which carry no Envelope, and THE Backend SHALL carry the numeric HTTP status on the HTTP line only (Decision G).
12. THE Backend SHALL use flask-smorest, registering every blueprint on one `Api` instance, and SHALL declare request bodies, query arguments, and responses of every endpoint with marshmallow schemas (Decision E).
13. IF request body or query validation fails, THEN THE Backend SHALL return HTTP 400 with the code `VALIDATION_ERROR` and an `error.details` object mapping each failing field name to a list of message strings from marshmallow, and SHALL NOT return HTTP 422 (Decisions E and G).
14. THE Backend SHALL keep each blueprint layered `routes.py → service.py → repository.py` with the marshmallow schemas in `schema.py` (Decision E).
15. THE Backend SHALL declare each success response with a schema that wraps the blueprint's payload schema in the Envelope (Decision E).
16. THE Backend SHALL declare the SQLAlchemy relationships `Board.columns`, `Board.members`, `Card.subtasks`, `Card.attachments`, and `Comment.replies`, each paired with its inverse through `back_populates`, declared with `lazy="raise"`, and without a delete cascade (Decision F).
17. THE Backend SHALL define no `to_dict` or other serialization method on any model (Decision F).
18. THE Backend SHALL ensure that services and schemas trigger no lazy load, by having each repository load the related rows it returns with `selectinload` or `joinedload` (Decision F).
19. THE Backend SHALL leave every list endpoint unpaged except the Inbox and the two activity feeds, which take `limit` and `before` as defined in Requirements 8.11 and 9.11; an unknown or non-numeric `limit` SHALL return HTTP 400 with the code `VALIDATION_ERROR` (Decision J).

### Requirement 20: Rate Limiting

**User Story:** As a system owner, I want repeated failed sign-ins, repeated wrong current passwords, and bulk availability checks to be blocked for a while, so that passwords cannot be guessed and the account list is harder to probe.

#### Acceptance Criteria

1. [RL-01] IF the Rate_Limiter has counted 5 failed login attempts for the same pair of lower-cased Identifier and Client_IP within the Rate_Limit_Window, THEN THE Backend SHALL return HTTP 429 with the code `RATE_LIMITED` for every further login attempt of that pair until fewer than 5 failures remain in the window (Decision O).
2. [RL-02] IF the Rate_Limiter has counted 20 failed login attempts from the same Client_IP within the Rate_Limit_Window across all Identifiers, THEN THE Backend SHALL return HTTP 429 with the code `RATE_LIMITED` for every further login attempt from that Client_IP until fewer than 20 failures remain.
3. [RL-03] WHEN a login succeeds, THE Backend SHALL delete the failed-attempt rows of that pair and SHALL leave the per-IP count unchanged.
4. [RL-04] THE Backend SHALL count one failed attempt for each login that ends in the generic HTTP 401, whether the Identifier is unknown or the password is wrong, and SHALL count no attempt for a login that ends in HTTP 400, or in HTTP 429.
5. [RL-05] WHEN the Rate_Limiter blocks a request, THE Backend SHALL return `{ "status": false, "message": string, "error": { "code": "RATE_LIMITED", "details": { "retry_after": integer } } }` with HTTP status 429 and a `Retry-After` header holding the same integer number of seconds (Decision O).
6. [RL-06] THE Backend SHALL compute `retry_after` as the number of whole seconds, rounded up and at least 1, until the oldest counted attempt that keeps the pair or the Client_IP at its limit leaves the Rate_Limit_Window.
7. [RL-07] [Withdrawn in V10 round 2, Decision Q] Registration is not rate limited; criterion 18 states the rule. The ID stays so that references do not move.
8. [RL-08] IF a Client_IP makes more than `RATE_LIMIT_AVAILABILITY_MAX` availability requests within the Rate_Limit_Window, THEN THE Backend SHALL return HTTP 429 with the code `RATE_LIMITED` for each further availability request; every availability request counts (kept by the specifier and reversible, Open Question 14).
9. [RL-09] THE Backend SHALL keep the attempt counts in the Postgres table `rate_limit_attempts`, SHALL serialize the check and the insert for one key with a transaction-scoped advisory lock, and SHALL commit a failed-attempt row before it returns the 401, so that counts hold across worker processes and survive the rollback that follows an error. Rate_Limiter rows are operational records, not state changes of the Board domain, so they write no Activity_Log row.
10. [RL-10] THE Backend SHALL read `RATE_LIMIT_WINDOW_SECONDS` (default 900), `RATE_LIMIT_LOGIN_PAIR_MAX` (default 5), `RATE_LIMIT_LOGIN_IP_MAX` (default 20), `RATE_LIMIT_AVAILABILITY_MAX` (default 60), and `RATE_LIMIT_CHANGE_PASSWORD_MAX` (default 5) from the environment, SHALL list each in `backend/.env.example` with a placeholder, and SHALL accept the same settings as arguments of the app factory, so that tests use small limits without setting `APP_ENV`.
11. [RL-11] THE Backend SHALL take the Client_IP from the connection's remote address, and SHALL read `X-Forwarded-For` only through the number of trusted proxies set in `TRUSTED_PROXY_COUNT` (default 0).
12. [RL-12] THE Backend SHALL store in `rate_limit_attempts` only a keyed hash of the Identifier-and-IP pair, of the IP, or of the user id (scope `change_password`), and never the plaintext Identifier or an Email.
13. [RL-13] WHEN the Rate_Limiter records an attempt, THE Backend SHALL delete the rows of that scope that are older than the Rate_Limit_Window.
14. [RL-14] WHILE a pair is blocked, THE Backend SHALL return HTTP 429 without comparing the password, so that a correct password does not unblock the pair.
15. [RL-15] WHEN a login response is HTTP 429, THE Frontend SHALL show the wait time as a countdown in minutes and seconds beside the form message, disable the submit button until the countdown ends, and then enable it and clear the message; THE Frontend SHALL read the wait from `error.details.retry_after`.
16. [RL-16] WHEN the availability check is blocked, THE Frontend SHALL stop on-blur checks until the wait ends and SHALL show no error for the field, because the 409 on submit stays authoritative (Requirement 1, criterion 50).
17. [RL-17] THE Backend SHALL list `Retry-After` in the CORS exposed headers.
18. [RL-18] THE Backend SHALL NOT rate limit `POST /api/auth/register` and SHALL keep no `register` scope in `rate_limit_attempts`, so that a registration request is answered only with 201, 400, or 409 (Decision Q; registration rate limiting deferred).
19. [RL-19] IF a signed-in user has had `RATE_LIMIT_CHANGE_PASSWORD_MAX` failed change-password attempts within the Rate_Limit_Window, THEN THE Backend SHALL return HTTP 429 with the code `RATE_LIMITED` for every further `POST /api/auth/change-password` call of that user until fewer failures remain; the counter is keyed by the user id and not by the Client_IP (Decision W, resolving Open Question 9).
20. [RL-20] THE Backend SHALL count one failed attempt for each change-password call that ends in HTTP 400 with `details.current_password`, and SHALL count no attempt for a call that ends in any other 400, in 401, or in 429; WHEN a change-password call succeeds, THE Backend SHALL delete that user's failed-attempt rows of the scope.
21. [RL-21] WHILE a user is blocked by criterion 19, THE Backend SHALL return HTTP 429 without comparing the current password, with the body, the `Retry-After` header, and the `retry_after` value of criteria 5 and 6.
22. [RL-22] WHEN a change-password response is HTTP 429, THE Frontend SHALL show the wait time as a countdown beside the form message, disable the Change password button until the countdown ends, and keep the session, because a 429 is not a 401.
23. [RL-23] THE Backend SHALL keep a `change_password` value in the scope column of `rate_limit_attempts` and SHALL purge the rows of that scope older than the Rate_Limit_Window when it records an attempt, as criterion 13 states for the other scopes.

### Requirement 24: Invite Link and Join Requests

**User Story:** As a Board_Owner, I want to invite people to my Board with a link and see who asked to join, so that the right people can request access and a Manager or Admin can approve them.

Note (V12, Decision AA): the Invite_Link is a second token, separate from the Public_Link. It never grants access by itself: it only lets a signed-in Member or Supervisor ask. Only a Manager or an Admin decides.

#### Acceptance Criteria

1. [INV-01] THE Backend SHALL store a nullable, unique `invite_token` on each Board (at least 256 bits from a cryptographically secure source, `secrets.token_urlsafe(32)`), where null means invites are off, and SHALL keep it out of every Activity_Log `metadata`, every log line, and every response other than the invite management endpoints of criteria 2 to 4 (Decision AA).
2. [INV-02] WHEN the Board_Owner, a Manager, or an Admin calls `POST /api/boards/{id}/invite` while invites are off, THE Backend SHALL generate and store an `invite_token`, write one `board.invite_enabled` Activity_Log row, and return HTTP 200 with `{ "enabled": true, "token": string, "path": "/invite/<token>" }`; WHILE invites are on, THE Backend SHALL return the existing token and write no row.
3. [INV-03] WHEN the Board_Owner, a Manager, or an Admin calls `POST /api/boards/{id}/invite/regenerate`, THE Backend SHALL replace the `invite_token`, write one `board.invite_regenerated` row, and make the previous link stop working at once; WHEN they call `DELETE /api/boards/{id}/invite`, THE Backend SHALL set `invite_token` to null, write one `board.invite_disabled` row when invites were on, and return HTTP 200 in either case.
4. [INV-04] WHEN the Board_Owner, a Manager, or an Admin calls `GET /api/boards/{id}/invite`, THE Backend SHALL return `{ "enabled": boolean, "token": string or null, "path": string or null }`.
5. [INV-05] IF any other signed-in user calls an endpoint of criteria 2 to 4, THEN THE Backend SHALL return HTTP 403, or HTTP 401 when no Token is present.
6. [INV-06] WHEN a signed-in user calls `GET /api/invite/{token}` with a current `invite_token` of a non-soft-deleted Board, THE Backend SHALL return HTTP 200 with `{ "board": { "id", "name", "description" }, "state": string, "request": { "id", "status" } or null }`, where `state` is `staff` for a Manager or an Admin, `member` for the Board_Owner or a BoardMember, `pending` when the user has a pending BoardJoinRequest, and `can_request` otherwise.
7. [INV-07] IF `GET /api/invite/{token}` or `POST /api/invite/{token}/requests` carries no Token, THEN THE Backend SHALL return HTTP 401, and IF the token is unknown, was disabled or replaced, or belongs to a soft-deleted Board, THEN THE Backend SHALL return the same HTTP 404 `NOT_FOUND` response in every case.
8. [INV-08] WHEN a signed-in Member or Supervisor who is neither the Board_Owner nor a BoardMember and has no pending request calls `POST /api/invite/{token}/requests`, THE Backend SHALL create a BoardJoinRequest with status `pending`, write one `board.join_requested` Activity_Log row, create one `board_join_requested` Notification for the Board_Owner and for every Manager and Admin in the same transaction, and return HTTP 201 with `{ "id", "board_id", "status", "created_at" }`.
9. [INV-09] IF a Manager or an Admin calls `POST /api/invite/{token}/requests`, THEN THE Backend SHALL return HTTP 400 with the code `VALIDATION_ERROR` and `error.details.role`, and create no row.
10. [INV-10] IF the caller is the Board_Owner or a BoardMember, or already has a pending request for that Board, THEN `POST /api/invite/{token}/requests` SHALL return HTTP 409 with the code `CONFLICT` and `error.details.board`, and create no row.
11. [INV-11] THE Backend SHALL enforce at most one `pending` BoardJoinRequest per `(board_id, user_id)` by a partial unique index, and SHALL map a violation raised by two simultaneous requests to the HTTP 409 of criterion 10.
12. [INV-12] WHEN a rejected requester calls `POST /api/invite/{token}/requests` again, THE Backend SHALL create a new `pending` request with no cooldown and leave the earlier rejected row unchanged.
13. [INV-13] WHEN the Board_Owner, a Manager, or an Admin calls `GET /api/boards/{id}/join-requests`, THE Backend SHALL return the `pending` requests of that Board, oldest first, each with `id`, `status`, `created_at`, and `user` as `{ id, full_name, username, email, avatar_url }` (the Email is returned only to the Board_Owner, a Manager, and an Admin, which are the only roles allowed to call this endpoint; Decisions M and S as amended in V12 round 2); the optional `?status=pending|approved|rejected|all` query SHALL select another set; any other signed-in user SHALL receive HTTP 403, or HTTP 401 with no Token.
14. [INV-14] WHEN a Manager or an Admin calls `PATCH /api/join-requests/{id}` with `{ "status": "approved" }` on a `pending` request, THE Backend SHALL set the status, set `decided_by` to the caller, create the BoardMember for the requester (no duplicate when one exists), write one `board.member_added` Activity_Log row, create one `board_added` Notification for the requester, and return HTTP 200 with the request, all in one transaction.
15. [INV-15] WHEN a Manager or an Admin calls `PATCH /api/join-requests/{id}` with `{ "status": "rejected" }` on a `pending` request, THE Backend SHALL set the status, set `decided_by`, write one `board.join_rejected` Activity_Log row, create one `board_join_rejected` Notification for the requester, and return HTTP 200, without creating a BoardMember.
16. [INV-16] IF a user who is not a Manager or an Admin, the Board_Owner included, calls `PATCH /api/join-requests/{id}`, THEN THE Backend SHALL return HTTP 403, or HTTP 401 with no Token; IF the id is unknown THE Backend SHALL return HTTP 404; IF the request is not `pending` THE Backend SHALL return HTTP 409 with the code `CONFLICT`; IF `status` is neither `approved` nor `rejected` THE Backend SHALL return HTTP 400 with the code `VALIDATION_ERROR`.
17. [INV-17] THE Backend SHALL leave pending requests pending when the Invite_Link is regenerated or disabled, because a request is a record of an action already taken.
18. [INV-18] THE Backend SHALL send `Cache-Control: private, no-store` on every `/api/invite` response, and THE Frontend SHALL send `Referrer-Policy: no-referrer` and `X-Robots-Tag: noindex` on every `/invite/{token}` page.
19. [INV-19] WHERE the viewer is the Board_Owner, a Manager, or an Admin, THE Frontend SHALL show an "Invite" button in the Board's App_Header that opens a modal with: the current state, a Generate action when invites are off, the full link with a click-to-copy control, Regenerate and Disable actions (each behind a `BaseConfirm` popover that says the old link stops working), and the list of pending join requests with the requester's Avatar_Image or Initials_Avatar, full name, Username, Email, and the request time.
20. [INV-20] WHERE the viewer is a Manager or an Admin, THE Frontend SHALL show Approve (primary) and Reject (secondary) on each pending request in the Invite modal; WHERE the viewer is the Board_Owner and not a Manager or an Admin, THE Frontend SHALL show the same list without those actions and with the note "A manager or an admin decides on requests."
21. [INV-21] WHERE the viewer can see pending requests and the Board has at least one, THE Frontend SHALL show the count as a badge on the Invite button.
22. [INV-22] WHEN a visitor without a Session_Cookie opens `/invite/{token}`, THE Frontend SHALL redirect to `/login?next=/invite/<token>`; WHEN the visitor signs in or registers there, THE Frontend SHALL return to `/invite/<token>` (Requirement 1, criteria 59 and 66).
23. [INV-23] WHILE the viewer is signed in and `state` is `can_request`, THE Frontend SHALL show the Board name, the description, and a "Request to join" button that calls `POST /api/invite/{token}/requests` and then shows "Request sent. You will get a notification when a manager or an admin decides."
24. [INV-24] WHILE `state` is `pending`, THE Frontend SHALL show "Your request is waiting for a decision." with no button; WHILE `state` is `member`, THE Frontend SHALL show "You are already a member of this board." with an Open board link; WHILE `state` is `staff`, THE Frontend SHALL show "You already have access to every board." with an Open board link.
25. [INV-25] IF the invite route answers HTTP 404, THEN THE Frontend SHALL show one page that says the invite link is not valid, without saying whether it was disabled, replaced, or never existed.
26. [INV-26] THE Backend SHALL record each BoardJoinRequest as `id`, `board_id`, `user_id`, `status` (`pending`, `approved`, or `rejected`), nullable `decided_by`, `created_at`, and `updated_at`.
27. [INV-27] THE Frontend SHALL show a requester's Email only in the pending list of the Invite modal, to the Board_Owner, a Manager, and an Admin, and SHALL show it in no Inbox row, Notification text, Activity_Log row, tooltip, `alt` text, or label (Decision S as amended in V12 round 2).
28. [INV-28] THE Backend SHALL return no Email in the response of `POST /api/invite/{token}/requests`, in the response of `PATCH /api/join-requests/{id}`, in any Notification payload, or in any Activity_Log `metadata` of the join-request actions, and SHALL read `User.email` for the pending list through the join of the request's `user_id` without copying it into `board_join_requests` (Decision S as amended in V12 round 2).

### Requirement 25: Card Modal Auto-Save

**User Story:** As a user who edits a Card, I want every change to save by itself and to see that it saved, so that I never lose an edit and never have to remember a Save button.

Note (V12, Decision AB): this requirement supersedes the draft model of Decision I and Decision J's sentence "attachment changes in the card modal wait for Save changes". Requirement 4 criteria 21, 30, 32, 35, and 43 and the "one save, one Activity_Log row" rule are superseded and carry a label. The Backend API of `PATCH /api/cards/{id}` does not change; the Frontend sends smaller requests.

#### Acceptance Criteria

1. [SAVE-01] THE Frontend SHALL show no "Save changes" button and keep no draft of the Card in the Card modal; the footer holds only Archive (secondary) and Delete (danger, behind a `BaseConfirm` popover), right-aligned (Decision AB).
2. [SAVE-02] WHEN the title field loses focus or the user presses Enter in it, and the trimmed value differs from the last saved value, THE Frontend SHALL send one `PATCH /api/cards/{id}` with `{ "title": value }`; WHEN the description field loses focus or the user presses Ctrl+Enter or Cmd+Enter in it, and the value differs, THE Frontend SHALL send one `PATCH` with `{ "description": value }`.
3. [SAVE-03] IF the title is empty after trimming, THEN THE Frontend SHALL send no request, show the inline error "Title is required." beside the field, and keep the field focused for editing.
4. [SAVE-04] WHEN the user confirms a value in the category popover, the priority popover, or the assignee popover (choosing an option or Remove), THE Frontend SHALL send one `PATCH` with only that field (`category_id`, `priority`, or `assignee_id`) and close the popover.
5. [SAVE-05] WHEN the user closes the dates popover and the start date, the end date, or both differ from the last saved values, THE Frontend SHALL send one `PATCH` with `start_date` and `end_date`; WHILE the popover is open and the pair is invalid (Requirement 4, criterion 32), THE Frontend SHALL send nothing and show the inline error.
6. [SAVE-06] WHEN the user adds a Subtask, toggles it, renames it, reorders it, or deletes it, THE Frontend SHALL send that one call (`POST /api/cards/{id}/subtasks`, `PATCH /api/subtasks/{id}`, or `DELETE /api/subtasks/{id}`) at once, and WHEN the user adds an Attachment link or picks an Attachment file, THE Frontend SHALL send `POST /api/cards/{id}/attachments` at once (Decision AB; supersedes Requirement 4, criterion 43).
7. [SAVE-07] WHILE a field's request is in flight, THE Frontend SHALL show "Saving…" beside that field; WHEN it succeeds, THE Frontend SHALL show "Saved" for 2 seconds and then nothing; IF it fails, THEN THE Frontend SHALL show the server message (`error.details` first, otherwise `message`) as an inline error with a Retry button beside that field, keep the field editable with the user's text, and keep the last saved value as the comparison base.
8. [SAVE-08] THE Frontend SHALL announce each field's state through an `aria-live="polite"` region beside the field, so that "Saving", "Saved", and the error reach assistive technology.
9. [SAVE-09] WHEN the response of a field's `PATCH` arrives, THE Frontend SHALL merge into the displayed Card only the fields that request sent, so that a later response never overwrites another field the user is still editing (last write wins per field).
10. [SAVE-10] THE Backend SHALL apply concurrent edits as last write wins: it SHALL carry no version or ETag check on Cards in V12, and two users editing the same field produce two `card.updated` rows, the later value stands.
11. [SAVE-11] WHEN a `PATCH /api/cards/{id}` changes no value, THE Backend SHALL return HTTP 200 and write no Activity_Log row; WHEN it changes at least one value, THE Backend SHALL write exactly one `card.updated` row whose `metadata.changes` lists only the fields that changed, so that one save writes one row and, because the Frontend sends one field per request (the two dates together), the row reads as one change (Decision AB; replaces the "one save, one row" rule of Decision I).
12. [SAVE-12] WHEN a Subtask or Attachment is added, changed, or removed, THE Backend SHALL write one Activity_Log row in the same transaction with the action `card.subtask_added`, `card.subtask_updated` (toggle, rename, or reorder), `card.subtask_removed`, `card.attachment_added`, or `card.attachment_removed`, and with `metadata` holding `card_title` and the Subtask title or the Attachment name, and THE Frontend SHALL describe each as a sentence in `describeActivity` (Requirement 8, criteria 9 and 10).
13. [SAVE-13] WHEN the user closes the Card modal (header icon, Escape, or a click on the backdrop) while a field has a pending blur save or a request in flight, THE Frontend SHALL send the pending save, wait for every in-flight request to finish, and then close; WHILE it waits, THE Frontend SHALL show "Saving…" in the header.
14. [SAVE-14] IF the user closes the Card modal while a field is in the failed state of criterion 7, THEN THE Frontend SHALL ask in a `BaseConfirm` dialog "Some changes were not saved. Close anyway?" and close only on confirmation (replaces the "unsaved changes" prompt of Requirement 4, criterion 43).
15. [SAVE-15] THE Frontend SHALL keep the Comment composer independent of every field save, and a posted Comment SHALL appear in the thread without touching the state of any other field (Requirement 7).
16. [SAVE-16] WHERE the viewer has no edit right on the Card (Requirement 4, criteria 8 and 9, and every viewer of the Shared_View), THE Frontend SHALL render the fields read-only with no save state.

### Requirement 26: Comment Deletion and Attachment Removal Confirmation

**User Story:** As a user, I want to delete my own comments and to be asked before an attachment is removed, so that I can retract what I wrote and never lose a file by a stray click.

Note (V12, Decision AC): `BaseConfirm` has two forms. The popover form is a small panel anchored to the trigger and is used for Delete Card, Delete Subtask, Remove Board member, Regenerate or Disable a Public_Link or Invite_Link, and Remove profile picture; Approve and Reject on a join request are not confirmed. The modal form is a centred dialog with a backdrop and focus trap and is used where the action removes content other people may rely on or removes more than one row: removing an Attachment and deleting a Comment. Requirement 4 criterion 44 is amended for Attachments only.

#### Acceptance Criteria

1. [DEL-01] WHEN a user activates Remove on an Attachment, THE Frontend SHALL open the modal form of `BaseConfirm` with the title "Remove attachment?", the Attachment's name, a danger "Remove" button, and a "Cancel" button, and SHALL call `DELETE /api/attachments/{id}` only after the user confirms (Decision AC; amends Requirement 4, criterion 44).
2. [DEL-02] WHEN the user confirms, THE Frontend SHALL remove the Attachment tile when the call returns HTTP 200; IF the call fails, THEN THE Frontend SHALL keep the tile and show the inline error with Retry beside the Attachments card.
3. [DEL-03] WHEN an Attachment with an uploaded file is removed, THE Backend SHALL delete the Attachment row and write one `card.attachment_removed` Activity_Log row in one transaction and SHALL delete the stored file after the commit.
4. [DEL-04] WHEN the author of a Comment or Reply calls `DELETE /api/comments/{id}` and still has Board_Access to the Card's Board, THE Backend SHALL delete that row and return HTTP 200 with `{ "deleted": n }`, where `n` is the number of rows removed (Decision AC).
5. [DEL-05] WHEN a Reply is deleted, THE Backend SHALL decrement the parent's `reply_count` by one in the same transaction, so that `reply_count` stays equal to the number of the parent's Replies.
6. [DEL-06] WHEN a top-level Comment that has Replies is deleted, THE Backend SHALL delete its Replies in the same transaction and return `n` equal to one plus the number of Replies.
7. [DEL-07] IF a signed-in user who is not the author calls `DELETE /api/comments/{id}`, a Manager and an Admin included, THEN THE Backend SHALL return HTTP 403; IF no Token is present THEN HTTP 401; IF the id is unknown THEN HTTP 404; and in each case THE Backend SHALL change nothing (Decision AC; Manager and Admin deletion of others' Comments is out of scope).
8. [DEL-08] WHEN a Comment or Reply is deleted, THE Backend SHALL write one `comment.deleted` Activity_Log row in the same transaction with `target_type` `card`, `target_id` the Card's id, and `metadata` holding `card_title`, `comment_id`, `is_reply`, and `deleted_replies`, and no part of the Comment's text, so that the append-only log stays intact and the removed text is not kept.

[DEL-09] THE Backend SHALL treat `comment.deleted` as the single documented exception to Requirement 4, criterion 29 for Comments: a Comment has no `deleted_at`, is hidden with its Card by the Card's `deleted_at`, and is physically removed only by the author's action of criterion 4; Subtask rows and Attachment rows follow Requirement 4, criterion 29 unchanged, and Activity_Log rows are never deleted (Requirement 8, criterion 2).
10. [DEL-10] WHERE the viewer is the author of a Comment or Reply on a Card they can open, THE Frontend SHALL show a Delete action on it; WHEN the user activates it, THE Frontend SHALL open the modal form of `BaseConfirm` with the title "Delete comment?" and, for a top-level Comment with Replies, the text "This also deletes its N replies." (N from `reply_count`), and SHALL remove the Comment or Reply and update the parent's reply count on HTTP 200.
11. [DEL-11] THE Frontend SHALL show no Delete action on another user's Comment and no Delete action in the Shared_View or to any viewer without Board_Access.

### Requirement 27: Subtask Permissions and Derived Progress

**User Story:** As a Member, I want to tick off the Subtasks of a Card assigned to me, and as any viewer I want the Card's progress to follow its Subtasks, so that the meter is never typed by hand and never out of date.

Note (V12, Decision AD): Requirement 4 criteria 12 to 14 already give the Assigned_Member the edit rights of a Subtask, so this decision does not reverse Decision 2; it states the exact matrix and makes the toggle an explicit, tested requirement. Reconciliation: the Card's `progress` was a stored, stretch column (Requirement 16, criterion 1) that no code writes yet; V12 makes it a computed, read-only field.

#### Acceptance Criteria

1. [SUB-01] THE Backend SHALL apply this Subtask matrix, each action also requiring Board_Access: toggle `is_done`, add, rename, reorder, and delete are allowed to a Manager, an Admin, and a Supervisor with Board_Staff_Access on any Card of the Board, and to a Member only on a Card whose `assignee_id` is that Member; every other combination returns HTTP 403, or HTTP 401 with no Token (Decision AD; Requirement 4, criteria 12 to 14).
2. [SUB-02] WHEN an Assigned_Member calls `PATCH /api/subtasks/{id}` with `{ "is_done": true }` or `{ "is_done": false }`, THE Backend SHALL persist the value, write one `card.subtask_updated` row, and return the Subtask.
3. [SUB-03] IF a Member calls any Subtask endpoint for a Card whose `assignee_id` is not that Member or is null, THEN THE Backend SHALL return HTTP 403 and change nothing (Decision 2).
4. [SUB-04] THE Backend SHALL compute `progress` on every Card payload as `(20 * done + total) // (2 * total)` (rounded half up, an integer from 0 to 10) when `total` is greater than 0, and as null when the Card has no Subtasks, where `done` and `total` count the Card's Subtasks, and SHALL also return `subtask_done_count` and `subtask_total_count`, all from the already loaded Subtasks with no extra query.
5. [SUB-05] IF a request body contains `progress`, THEN THE Backend SHALL return HTTP 400 with the code `VALIDATION_ERROR` and `error.details.progress`, because `progress` is derived (Decision AD; supersedes Requirement 16, criterion 1 for `progress`; `views_count` stays stored and stretch).
6. [SUB-06] WHERE a Card has at least one Subtask, THE Frontend SHALL show a progress meter with the text "done of total" on the board Card and in the Card modal's Subtasks card; WHERE a Card has none, THE Frontend SHALL show no meter on the board Card and the text "No subtasks yet" in the modal.
7. [SUB-07] WHEN a Subtask is toggled, added, or deleted, THE Frontend SHALL update the meter from the response without a reload.
8. [SUB-08] WHERE the viewer is a Member and the Card is assigned to that Member, THE Frontend SHALL show enabled Subtask checkboxes; WHERE the Card is assigned to someone else, THE Frontend SHALL show them disabled; in the Shared_View and for any viewer without Board_Access THE Frontend SHALL show them disabled and send no request (Requirement 23, criterion 7).
9. [SUB-09] THE Backend SHALL include `progress`, `subtask_done_count`, and `subtask_total_count` in the shared Card payload, which already carries Subtasks (Requirement 18, criterion 11).

### Requirement 28: Inbox Navigation and Notification Types

**User Story:** As a signed-in user, I want to open what a notification is about with one click, so that I land on the right Card or Board instead of hunting for it.

Note (V12, Decision AE): this requirement amends Requirement 9 (types and links) and Glossary Notification. A Notification of type `deadline` or `assigned` keeps its V2 rules.

[INB-01] THE Backend SHALL store each Notification with `type` (`assigned`, `deadline`, `board_join_requested`, `board_added`, or `board_join_rejected`), nullable `card_id`, nullable `board_id` (always set by the Backend on new rows), nullable `actor_id`, nullable `join_request_id`, `notify_date`, `is_read` (default false), and `created_at`, with a CHECK that a card type has a `card_id` and a board type has a `board_id` and no `card_id` (Decision AE).
2. [INB-02] THE Backend SHALL deduplicate Notifications with three partial unique indexes: `(user_id, card_id, type, notify_date)` where `card_id IS NOT NULL`; `(user_id, type, join_request_id)` where `join_request_id IS NOT NULL`; and `(user_id, type, board_id, notify_date)` where `card_id IS NULL AND join_request_id IS NULL`, so that rows with a null `card_id` stay deduplicated, every join request notifies once per user, and a null never makes two rows distinct (Decision AE).

[INB-05] THE Frontend SHALL render each Inbox row as one link whose `href` is `/boards/{board_id}?card={card_id}` for `assigned` and `deadline`, `/boards/{board_id}?invite=1` for `board_join_requested`, `/boards/{board_id}` for `board_added`, and `/boards` for `board_join_rejected` (the requester has no access to the Board), so that the row is reachable and activatable by keyboard (Enter) and by middle click (Decision AE).
6. [INB-06] WHEN the user activates an Inbox row, THE Frontend SHALL send `PATCH /api/notifications/{id}/read`, lower the unread count at once, navigate without waiting for the response, and close the Side_Panel.
7. [INB-07] WHEN the Board page opens with `?card=<id>`, THE Frontend SHALL open that Card's modal after the Board loads, and WHEN the modal closes THE Frontend SHALL remove the parameter.
8. [INB-08] IF the Card of `?card=` is soft-deleted, unknown, or on another Board, THEN THE Frontend SHALL show the notice "This card is no longer available." above the Board and open no modal; IF the Card is archived, THEN THE Frontend SHALL show "This card is archived." and open no modal.
9. [INB-09] IF the Board answers HTTP 403 or HTTP 404 for a Notification target, THEN THE Frontend SHALL show a page with the message "You no longer have access to this board, or it was removed." and a link to Home, never a blank page or the raw error.
10. [INB-10] WHEN the Board page opens with `?invite=1` and the viewer is the Board_Owner, a Manager, or an Admin, THE Frontend SHALL open the Invite modal on the pending-request list (Requirement 24, criterion 19); for any other viewer THE Frontend SHALL ignore the parameter.
11. [INB-11] THE Frontend SHALL write each new Notification type as a sentence naming the actor and the Board: "Ada Lovelace asked to join "Board name"", "You were added to "Board name"", and "Your request to join "Board name" was declined".

[PRO-03] THE Frontend SHALL build the Profile_Page from the existing tokens only: controls 40 pixels high (compact buttons 32 pixels), 16 pixel padding in every card, 24 pixels between cards, titles and labels at the sizes of Requirement 14, criterion 20, and no hard-coded colour or arbitrary value.
4. [PRO-04] THE Frontend SHALL keep every field, action, validation message, and endpoint of Requirement 19 on the Profile_Page, and the avatar preview SHALL keep its size at every width.

### Requirement 32: Document Titles

**User Story:** As a user with several tabs open, I want each tab to say where I am, so that I can find RevoTask and the page I need at a glance.

Note (V13, Decision AI): amends Requirement 21 criterion BRAND-11 (the suffix "· RevoTask") and every page `metadata` title of earlier versions. The root title stays `RevoTask`.

#### Acceptance Criteria

1. [TITLE-01] THE Frontend SHALL set the document title of every page to `RevoTask | <name>` through the Next.js `metadata` API, where `<name>` is the page or panel the user has open, so that the brand comes first and the name follows; the root layout SHALL define `title.default` `RevoTask` and `title.template` `RevoTask | %s`.
2. [TITLE-02] THE Frontend SHALL use these names: Home `Home`; a Board its name (`RevoTask | Alpha Board`); Categories `Categories · <Board name>`; Profile `Profile`; Users `Users`; an invitation `Invitation`; a Shared_View `Shared · <Board name>`; sign-in `Log in`; registration `Register`; the session-expired and not-valid pages `Unavailable`.
3. [TITLE-03] THE Frontend SHALL build the Board and Categories titles with `generateMetadata` from the Board the page already loads (no second request), and SHALL fall back to `RevoTask | Board` when the Board cannot be read; THE title SHALL NOT contain a Token, an invite token, a Share_Token, an Email, or a Comment.

[TITLE-04] WHEN the Inbox or the Activity panel is open, THE Frontend SHALL set the title to `RevoTask | Inbox` or `RevoTask | Activity` (with the unread count as `RevoTask | Inbox (3)` when it is above zero), and SHALL restore the title of the page when the panel closes; the title SHALL follow the panel the user opened last.

6. [TITLE-06] THE Frontend SHALL escape no title by hand (React and Next.js do) and SHALL cut a title longer than 60 characters with "…" so that the tab stays readable.
7. [TITLE-07] THE Frontend SHALL keep `robots` `noindex` on the invitation and Shared_View pages, and the other `metadata` fields (description, icons by file convention) SHALL not change.
8. [TITLE-08] THE System SHALL include `vitest` tests for the title builder (a pure function: name in, title out, 60 character cut, panel and unread count) and one test per route that renders its title; the e2e suite SHALL assert `document.title` of `/login` and `/register` only (read-only, Requirement 1 criteria 65 to 72 unchanged).

### Requirement 33: Production Topology

**User Story:** As the product owner, I want RevoTask to run on my server behind Nginx and return after a reboot, so that people can use it from the internet.

#### Acceptance Criteria

1. [DEP-01] THE System SHALL run the Backend, the Frontend, and a deadline scheduler as Docker Compose services built from the monorepo, each as a non-root user.
2. [DEP-02] THE System SHALL use the PostgreSQL installed on the server at `localhost:5432`, database `revoboard_db`, owned by the non-superuser role `revou`, and SHALL provide idempotent setup SQL that takes the password at run time.
3. [DEP-03] THE System SHALL run every service with `network_mode: host`, binding the Backend to `127.0.0.1:5001` and the Frontend to `127.0.0.1:3000`.
4. [DEP-04] THE Backend SHALL be served by Gunicorn with 3 workers.
5. [DEP-05] THE System SHALL provide a new Nginx site file that serves one origin, sends `/api/` to the Backend and every other path to the Frontend, preserves the public host and port, overwrites `X-Forwarded-For` with the client address, and limits the request body (Open Question 35). THE Backend SHALL run with `TRUSTED_PROXY_COUNT=1`.
6. [DEP-06] THE Frontend SHALL call `/api` on the current origin from the browser and SHALL read an absolute loopback Backend URL from `INTERNAL_API_URL` on the server, so that one build works on the IP address and on the domain.
7. [DEP-07] THE Frontend SHALL send every redirect, `/session-expired` included, to the public origin or as a relative path, and never to `localhost` or a container address.
8. [DEP-08] WHEN the server boots, THE System SHALL start PostgreSQL, Nginx, and Docker through their enabled system services, and every Compose service through `restart: unless-stopped`.
9. [DEP-09] THE System SHALL run `flask notify-deadlines` at least hourly from the scheduler service; a repeated run SHALL create no duplicate Notification.
10. [DEP-10] THE System SHALL keep uploads outside the checkout and the images, so that they survive a deploy and a reboot.
11. [DEP-11] THE System SHALL keep every secret and password out of the repository, the images, and the CI logs; application secrets SHALL live only in a server file with mode 600.
12. [DEP-12] THE System SHALL rotate container logs with the `json-file` driver, `max-size` 10 MB and `max-file` 3.
13. [DEP-13] UNTIL the domain and TLS are configured, THE System SHALL accept plain HTTP on the server IP and port 8082. The later TLS change SHALL add `Secure` to the Session_Cookie and update `ALLOWED_ORIGINS`. The planned domain is `revoboard.belajardeploy.web.id`.

### Requirement 34: Continuous Integration and Deployment

**User Story:** As the product owner, I want a push to master to be tested in a separate environment and then deployed, so that a broken build does not reach production.

#### Acceptance Criteria

1. [CICD-01] WHEN a pull request targets `master` or a commit is pushed to `master`, THE System SHALL run `pytest`, `tsc --noEmit`, `vitest run`, and `next build` in GitHub Actions.
2. [CICD-02] WHEN those checks pass, THE System SHALL build both images and start the production Compose stack in the CI runner against a throwaway PostgreSQL with throwaway secrets, starting from an empty database.
3. [CICD-03] THE smoke test SHALL verify the migrations, a second start, `/api/health`, login with a seeded test user, a server-rendered Board page, and the redirect target of `/session-expired`, all through Nginx.
4. [CICD-04] WHEN both jobs pass on a push to `master`, and only then, THE System SHALL deploy that exact commit over SSH with a pinned host key and build the images on the server, tagged with the commit SHA.
5. [CICD-05] THE System SHALL run one deployment at a time and SHALL NOT cancel a running deployment.
6. [CICD-06] BEFORE it replaces the running services, THE System SHALL back up the database (Open Question 34).
7. [CICD-07] IF the health check fails after a deploy, THEN THE System SHALL restart the previous images without running migrations, SHALL leave the schema as it is, and SHALL report the job as failed.
8. [CICD-08] THE System SHALL require each later migration to stay compatible with the previous release, because a rollback does not downgrade the schema.

### Requirement 35: Health Endpoint

**User Story:** As the operator, I want one endpoint that says whether the Backend works, so that deploys and health checks can decide automatically.

#### Acceptance Criteria

1. [HLT-01] WHEN `GET /api/health` is called without a Token and the database answers `SELECT 1`, THE Backend SHALL return 200 in the standard Envelope.
2. [HLT-02] IF the database does not answer, THEN THE Backend SHALL return 503 in the standard error Envelope within 5 seconds, without exception text, host, user, or connection string.
3. [HLT-03] THE Backend SHALL apply no rate limit to this endpoint, SHALL follow the routes, service, and repository layers, and SHALL list it in `openapi.json` and `API.md`.

### Requirement 36: Demo Seed

**User Story:** As the product owner, I want demo data in the deployed app, so that I can show it working.

#### Acceptance Criteria

1. [SEED-01] THE System SHALL document a manual, one-time `flask seed-data` command in a one-off container that alone receives `APP_ENV=development`, after the first migration.
2. [SEED-02] THE System SHALL take the seed password at run time and SHALL NOT write it to the repository, the server environment file, or the shell history.
3. [SEED-03] THE running Backend SHALL keep `APP_ENV=production`, the API documentation SHALL stay hidden, and no start or deploy step SHALL run a seed.

### Requirement 37: Migrations on Start

**User Story:** As the operator, I want the Backend to migrate on start without risk to data, so that a deploy needs no manual step.

#### Acceptance Criteria

1. [MIG-01] WHEN the Backend container starts normally, THE System SHALL run `flask db upgrade` once before Gunicorn starts and SHALL NOT start Gunicorn if it fails; a rollback start SHALL skip this step.
2. [MIG-02] WHEN the V10 or V12 migration runs outside development and testing and `users` is empty, THE migration SHALL apply its schema changes without `TRUNCATE`.
3. [MIG-03] IF either migration runs outside development and testing and `users` has rows, THEN THE migration SHALL abort with no change. Behaviour in development and testing SHALL NOT change.
