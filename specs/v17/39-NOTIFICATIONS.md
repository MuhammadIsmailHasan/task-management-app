# Notifications, V17 (draft)
### Requirement 57: Notification Preferences
**User Story:** As an assignee, I want to choose which events about my Cards reach my Inbox, so that I see what matters and nothing else.
This requirement adds five Notification types and per-user switches (Decision BI). It amends Requirement 9 (types and the Inbox), Requirement 28 (the type list and the Inbox links), and the `Notification` rule of `data-model.md`. The `assigned`, `board_join_requested`, `board_added`, and `board_join_rejected` types of V12 are not preference-controlled and keep their behaviour. In-app notifications only: email notifications are out of scope (exclusion 1).
#### Acceptance Criteria
**Data**
1. [NPF-01] THE Backend SHALL add the table `notification_preferences` with `id` (UUID), `user_id` (foreign key, not null), `type` (string, not null), `enabled` (boolean, not null), `created_at`, and `updated_at`, with a unique index on `(user_id, type)`, in migration 4. A missing row for a user and type means enabled, so no backfill is needed.
2. [NPF-02] THE Backend SHALL define five preference types: `comment_on_assigned` (another user comments or replies on a Card assigned to me), `due_today` (a Card assigned to me is due today), `due_tomorrow` (a Card assigned to me is due tomorrow, the H-1 reminder), `assigned_card_changed` (a Card assigned to me is moved to another Column, archived, or deleted), and `subtask_on_assigned` (a Subtask on a Card assigned to me is created, its title or done state changes, or it is deleted; a reorder alone does not count). EACH is also a value of `Notification.type`; migration 4 SHALL extend the type check or enum and keep `assigned`, `deadline`, and the three board types.
**Creation rules**
3. [NPF-03] THE Backend SHALL create a notification of a preference type only when the recipient has that type enabled, in the same transaction as the triggering action (backend steering rule), with `type`, `card_id`, `board_id`, `actor_id` (null for the due types), and `notify_date`. THE recipient is the Card's assignee at that moment; a Card with no assignee notifies no one. THE actor SHALL never notify themselves: when the actor is the assignee, no row is created. NO row is created for an inactive user (ADM-07).
4. [NPF-04] WHEN a comment or a reply is created on a Card, THE Backend SHALL create one `comment_on_assigned` notification for the assignee (one per comment, even when a reply also targets another author). WHEN a Card is moved to another Column, archived, or soft-deleted by a user who is not its assignee, THE Backend SHALL create one `assigned_card_changed` notification; a reorder inside the same Column, a field edit, and a restore SHALL NOT. WHEN a Subtask of a Card is created, changed (title or `is_done`), or deleted by a user who is not the assignee, THE Backend SHALL create one `subtask_on_assigned` notification.
5. [NPF-05] THE notification SHALL carry no comment text, no Subtask title, no Email, and no token: the Inbox row is rebuilt from `type`, `actor_name`, `card_title`, and `board_name` (Requirement 28, criterion on Notification fields), so a deleted comment or Subtask leaves no copy of its text (V12 comment deletion rule). THE Backend SHALL add `board_slug` to the payload (SLUG-07).
6. [NPF-06] THE dedupe indexes of V12 SHALL be changed so that event notifications are never refused: THE card-row unique index `uq_notifications_card` SHALL apply only to the types `assigned`, `deadline`, `due_today`, and `due_tomorrow` (`postgresql_where` and `sqlite_where` on `card_id IS NOT NULL AND type IN (...)`), so a second comment, move, or Subtask change on the same day on the same Card creates a second row (Open Question 56). THE index for join rows and the index for other board rows stay.
**Endpoints**
7. [NPF-07] THE Backend SHALL provide `GET /api/me/notification-preferences`, returning `{ "preferences": [ { "type", "enabled" } ] }` with exactly the five types in the order of NPF-02, `enabled` true where no row exists; and `PUT /api/me/notification-preferences` with the body `{ "preferences": [ { "type", "enabled" } ] }` of one to five distinct entries, which upserts the listed types in one transaction and returns the same shape as `GET`. AN unknown type, a duplicate type, an empty list, or a non-boolean `enabled` SHALL receive HTTP 400 `VALIDATION_ERROR` with `details`. BOTH routes are scoped to the signed-in user (no `user_id` in the path or body), return 401 without a Token, and live in the `notifications` blueprint with `@blp.arguments` and `@blp.response`.
8. [NPF-08] THE Frontend SHALL show the switches in the Notifications tab of the Profile (PRF-06) and SHALL show each type's Inbox row text: "<Actor> commented on “<Card>”", "“<Card>” is due today", "“<Card>” is due tomorrow", "<Actor> <action> “<Card>”" where `action` is `moved`, `archived`, or `deleted` (NPF-09), and "<Actor> updated a subtask on “<Card>”". THE `hrefFor` function SHALL open the Card (`cardPath(slug, id)`) for `comment_on_assigned`, `due_today`, `due_tomorrow`, `subtask_on_assigned`, and `assigned_card_changed` of a moved Card, and the Board for an archived or deleted Card with the not-available message of Requirement 28.
9. [NPF-09] THE `assigned_card_changed` Notification payload SHALL carry `action` (`moved`, `archived`, or `deleted`), stored in a nullable `Notification.action` column added by migration 4; no other type carries it.
### Requirement 58: Due-Date Job
**User Story:** As an assignee, I want a reminder on the day a Card is due and the day before, so that I do not miss a deadline.
This requirement supersedes Requirement 9 criteria 2 and 3 (the daily `deadline` job and its idempotence) and the scheduler of Requirement 33 and 37 (Decision BI, Open Question 56). Reference for the Inbox row: `11-inbox-desktop.png`.
#### Acceptance Criteria
1. [DUE-01] THE Backend SHALL provide the Flask CLI command `flask notify-due` in `app/jobs/due.py`, registered in the app factory, run every 15 minutes (OQ50). IT SHALL take "today" and "tomorrow" as dates in `APP_TIMEZONE` at the time of the run, with no per-user timezone, and SHALL print one line of counts (`due_today=N due_tomorrow=M skipped=K`) and exit with 0, or non-zero when an unexpected error occurs.
2. [DUE-02] THE command SHALL create a `due_today` notification for the assignee of each Card whose `end_date` is today and a `due_tomorrow` notification for each whose `end_date` is tomorrow, for Cards that are not soft-deleted, not archived, not in the Done_Column, and have an assignee who is active, respecting the assignee's preference (NPF-03). THE `notify_date` is today's date in `APP_TIMEZONE`.
3. [DUE-03] THE command SHALL be idempotent: it SHALL insert with `ON CONFLICT DO NOTHING` against the unique key `(user_id, card_id, type, notify_date)` of the partial index of NPF-06, so a second run on the same date inserts nothing and an overlapping run cannot create a duplicate (Property 76). IT SHALL also take a PostgreSQL advisory lock for its duration and exit 0 at once when another run holds it.
4. [DUE-04] A Card whose `end_date` is changed during the day SHALL be picked up by the next run: a Card moved to today after the first run gets its `due_today` at the next 15 minute run; a Card that was due today and is moved to a later date keeps the notification it already received. THE first run after local midnight creates the day's notifications; the spec does not hold them for a working hour.
5. [DUE-05] THE command SHALL create no `deadline` notification (the V12 type is no longer produced; existing rows still display). THE `app/jobs/deadlines.py` module and its scheduler hook SHALL be replaced by `due.py`; the tests of `test_scheduler.py` SHALL be updated for the new command, not deleted.
6. [DUE-06] THE deploy scripts SHALL install the schedule `*/15 * * * *` running `flask notify-due` with the application environment, and `deploy/README.md` SHALL document it, its log file, and how to run it by hand. WHERE the server cannot run cron (the unprivileged container of Open Question 31), THE bare-mode `supervisord` configuration SHALL run a program that loops `flask notify-due` then `sleep 900`, and the Docker mode SHALL run the same loop as a service named `scheduler`. THE scripts SHALL NOT start both a cron entry and the loop.
7. [DUE-07] THE command SHALL log counts and ids only (no Card titles, no Email), SHALL finish a run over 10000 candidate Cards with a number of queries that does not depend on the number of Cards (one select for candidates joined to preferences, one bulk insert), and SHALL be covered by tests on PostgreSQL for the unique key and the advisory lock and on SQLite for the logic (Requirement 15).
