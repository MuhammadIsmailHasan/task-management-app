# Account Activation and Email, V17 (draft)
### Requirement 59: Account Activation and Email
**User Story:** As the product owner, I want every new account to prove it owns its email address, and email changes to be confirmed, so that accounts are real and an address cannot be taken over by typing it.
This requirement amends Requirement 1 (register and login) and Requirement 19, and adds the mail transport used by Requirements 54 and 59 (Decision BJ). `email_verified_at` is separate from `is_active` (Requirement 53): the two have different codes and messages. Activation uses the Email_Token table for both the verification link and the email-change link.
#### Acceptance Criteria
**Data and rules**
1. [ACT-01] THE Backend SHALL add `users.email_verified_at` (nullable timestamp with time zone) in migration 3. A user with a null value SHALL NOT sign in: `POST /api/auth/login` SHALL return HTTP 403 with the code `ACCOUNT_NOT_ACTIVATED` and the message "Confirm your email address first" only after the identifier and password have both matched (a wrong identifier or password SHALL return the usual 401, so the code never reveals that an account exists). THE two states SHALL differ: `ACCOUNT_NOT_ACTIVATED` (403, "Confirm your email address first") and `ACCOUNT_DISABLED` (403, "This account is disabled"); WHEN both apply, `ACCOUNT_DISABLED` wins (ADM-07). A login refused with either code SHALL add no failure row to the rate limiter (the password was correct).
2. [ACT-02] WHEN a visitor calls `POST /api/auth/register`, THE Backend SHALL create the user with `email_verified_at` null, create an Email_Token of purpose `verify_email` that expires 24 hours later, send the verification email after the commit, and return HTTP 201 with `data` of `{ "user": {...}, "token": null }` (amends the shared shape of the auth rule: register returns no Token). NO Token SHALL be issued before verification (Property 77).
3. [ACT-03] THE Backend SHALL provide `POST /api/auth/verify` with `{ "token": string }` (no Token needed): it SHALL look up the SHA-256 hash of the value among unused tokens, and WHEN the token is valid and unexpired, mark it used in the same transaction, and for `verify_email` set `email_verified_at` to now, and for `change_email` replace `users.email` with `pending_email` and clear it (PRF-03), and return HTTP 200 with `data` of `{ "purpose" }`. IF the value is unknown or already used, THEN it SHALL return HTTP 400 `TOKEN_INVALID`; IF it is expired, THEN HTTP 400 `TOKEN_EXPIRED`. A token SHALL work once; the second call receives `TOKEN_INVALID`. THE request SHALL NOT sign the user in.
4. [ACT-04] THE Backend SHALL provide `POST /api/auth/resend-verification` with `{ "email": string }` (no Token needed). IT SHALL always return HTTP 200 with the same message ("If that address needs confirming, a new link was sent") whether or not the address exists or is already verified, so it reveals nothing; IT SHALL invalidate the user's earlier unused `verify_email` tokens and create a new one only when the user exists and is not verified. IT SHALL be rate limited under a new scope `resend_verification` of `RateLimitAttempt` (Requirement 20, the shared Postgres limiter, key = a keyed hash of the lower-cased email plus the client address, and a per-address bucket), with thresholds from environment variables (`RATE_LIMIT_RESEND_VERIFICATION_MAX`, default 3 per email and address and 10 per address in `RATE_LIMIT_WINDOW_SECONDS`), returning HTTP 429 `RATE_LIMITED` with `retry_after` and `Retry-After`. THE same limiter protects `POST /api/auth/me/email/resend`.
5. [ACT-05] THE migration SHALL set `email_verified_at` to the migration time for every existing user, so no one is locked out. A user created by an Admin through `POST /api/users` SHALL be verified at creation, and `flask seed-users` and `flask seed-data` SHALL create verified users (Requirement 36).
6. [ACT-06] THE Backend SHALL store tokens only as hashes in the `email_tokens` table: `id` (UUID), `user_id` (foreign key, not null), `purpose` (`verify_email` or `change_email`), `token_hash` (string, unique, the SHA-256 hex digest of the token), `expires_at` (not null), `used_at` (nullable), and `created_at`. A token SHALL be at least 256 bits from `secrets.token_urlsafe(32)`, SHALL expire 24 hours after creation for both purposes, SHALL appear only in the email body and the one link, and SHALL NOT appear in a log, an Activity_Log row, a notification, an error message, or an API response (the `token` of the register response is the sign-in Token and is null). THE `email_tokens` table is append and mark-used; rows are not updated otherwise, and expired rows MAY be deleted by `flask purge-email-tokens` (optional, not scheduled).
**Frontend**
7. [ACT-07] THE Frontend SHALL, after a successful register, go to `/app/verify` showing "Check your email" with the address (kept in `sessionStorage`, not the URL), the sentence "We sent a link to confirm your address. It expires in 24 hours.", a "Resend email" button (disabled with a mm:ss countdown on a 429, as the login form does), and a link to sign in. WHEN `/app/verify?token=...` loads, THE Frontend SHALL call `POST /api/auth/verify` once and show "Email confirmed" with a "Sign in" button (for `verify_email`) or "Email address updated" (for `change_email`), or an error state with "Send a new link" (for `TOKEN_EXPIRED` and `TOKEN_INVALID`). THE page SHALL send `Referrer-Policy: no-referrer` and `X-Robots-Tag: noindex` (the token must not leak) and SHALL remove the token from the address bar after reading it. WHEN login returns `ACCOUNT_NOT_ACTIVATED`, THE login form SHALL show the message and a "Resend confirmation email" action; WHEN it returns `ACCOUNT_DISABLED`, the form SHALL show the message and no resend.
**Mail transport**
8. [ACT-08] THE Backend SHALL send mail through one module, `app/common/mail.py`, with two backends chosen by `MAIL_BACKEND`: `smtp` and `console` (the default in development and testing; `smtp` is required when `APP_ENV` is production). THE `smtp` backend SHALL use Gmail SMTP (`smtp.gmail.com`, port 587, STARTTLS, an app password) configured only by `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, and `MAIL_FROM`, and `PUBLIC_BASE_URL` for the links (for example `https://revoboard.example/app/verify?token=...`). THE `console` backend SHALL write the message to the application log without the SMTP credentials, and tests SHALL use an in-memory outbox. NO credential SHALL appear in code, a committed file, a log, or an error message; `backend/.env.example` SHALL list the variables empty (Requirement 33 and `tech.md`). THE startup SHALL fail with a clear message when `MAIL_BACKEND=smtp` and any of the five variables is empty.
9. [ACT-09] THE Backend SHALL send each email after the database commit (never inside the transaction) from a small bounded worker so the request does not wait for SMTP; a failed send SHALL be logged (user id, purpose, error class; no address, no token) and SHALL NOT fail the request or roll anything back, with one retry after 5 seconds. EACH message SHALL be plain text with a simple HTML part, carry the product name, state what happened, and contain no password. THE messages are: "Confirm your RevoBoard email" (verification), "Confirm your new RevoBoard email" (email change, sent to the new address), and "Your RevoBoard password was changed" (PRF-05, sent to the confirmed address).
10. [ACT-10] THE `.env.example` files, `compose.yaml`, `deploy/bare/supervisor.conf`, the server environment template, and `deploy/README.md` SHALL list `MAIL_BACKEND`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `MAIL_FROM`, `PUBLIC_BASE_URL`, and `RATE_LIMIT_RESEND_VERIFICATION_MAX`, with a note that a Gmail account needs 2-step verification and an app password (Open Question 64).
11. [ACT-11] THE Backend SHALL document the new routes and codes (`ACCOUNT_NOT_ACTIVATED`, `ACCOUNT_DISABLED`, `TOKEN_INVALID`, `TOKEN_EXPIRED`) in `openapi.json` and `API.md`, SHALL keep `GET /api/auth/availability` and the login rate limit as they are, and SHALL regenerate both documents.
12. [ACT-12] THE Frontend SHALL keep the visitor's destination through register, verification, and sign-in, so an invite link still leads to its Join_Request (Open Question 69): the register and login pages accept `?next=<safe path>` under the PATH-05 rules; WHEN register succeeds, THE Frontend SHALL store `next` in `sessionStorage` with the address and go to `/app/verify`; THE "Sign in" button after "Email confirmed" SHALL go to `/app/login?next=<stored next>` when the verification happens in the same browser, and to `/app/login` otherwise; after sign-in THE Frontend SHALL go to `next` when it is a safe path. THE signed-out invite page's "Create account" and "Sign in" links SHALL pass `next=/app/invite/{token}`. THE verification email link SHALL NOT carry `next` (no invite token in an email the Backend writes), and `next` SHALL never be sent to the Backend.
