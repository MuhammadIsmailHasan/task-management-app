# Columns and Board Views, V17 (draft)
### Requirement 49: Column CRUD
**User Story:** As a Board_Owner, I want to create, rename, reorder, and delete the Columns of my Board, so that its workflow fits my team, without losing finished work.
This requirement amends Requirement 3 criteria 4 and 5 and Requirement 2 criterion 6, which let a Manager, an Admin, or a Supervisor with Board_Access create Columns: from V17 the Board_Owner, a Manager, and an Admin manage Columns, and a Supervisor who is only a BoardMember does not (Decision BC, Open Question 55, answered by the owner in round 2). The Default_Columns of Requirement 3 criterion 1 stay. Reference: the Column header of `01-board-desktop.png`; the new controls use the Component_Recipes.
#### Acceptance Criteria
**Permissions**
1. [COL-01] THE Backend SHALL allow only the Board_Owner of a Board, a Manager, and an Admin to create, rename, reorder, and delete its Columns, with `@require_role("supervisor", "manager", "admin")` plus an ownership check in the service for a Supervisor. EVERY other user, a Supervisor who is only a BoardMember and a Member included, SHALL receive HTTP 403, and a request without a Token HTTP 401 (Requirement 13). A Board with a null `owner_id` is managed by a Manager or an Admin (Open Question 55).
**Endpoints**
2. [COL-02] THE Backend SHALL provide: `POST /api/boards/{board_id}/columns` (body `name`; appends with the next `order`), `PATCH /api/columns/{id}` (body `name`), `PATCH /api/columns/{id}/move` (body `position`, a 0-based integer index among the Board's Columns), and `DELETE /api/columns/{id}`, each with `@blp.arguments` and `@blp.response` and the Envelope, in the `columns` blueprint (`routes.py`, `service.py`, `repository.py`, `schema.py`). A `name` is trimmed, 1 to 255 characters (the existing column length), and unique within the Board when compared case-insensitively; a duplicate SHALL receive HTTP 409 `CONFLICT` with `details.name`. A `position` outside `0..n-1` SHALL receive HTTP 400 `VALIDATION_ERROR`.
3. [COL-03] WHEN a Column is reordered, THE Backend SHALL renumber the Board's Columns `0.0, 1.0, 2.0, ...` in the new order in one transaction, so no gap or tie remains. THE Done_Column MAY be reordered (criterion 5).
4. [COL-04] EVERY Column create, rename, reorder, and delete SHALL write one ActivityLog row in the same transaction (`column.created`, `column.renamed` with the old and new name, `column.moved` with the old and new position, `column.deleted` with the name and no Card text), and SHALL NOT notify anyone.
**Deleting**
5. [COL-05] IF a Column to delete holds one or more Open_Cards or other active Cards (not archived and not soft-deleted), THEN THE Backend SHALL return HTTP 409 with the code `COLUMN_NOT_EMPTY` and `error.details` of `{ "count": n }`, and SHALL delete nothing. THE Frontend SHALL show "Move or archive its N cards first." (singular "its 1 card") in the ConfirmDialog's error area and in an `aria-live="polite"` region.
6. [COL-06] WHEN a Column to delete holds only soft-deleted Cards, THE Backend SHALL set their `column_id` to null in the same transaction and then delete the Column row. Archived Cards have no Column (COL-07) and never block a delete. A Column delete SHALL be a hard delete of the Column row; Boards and Cards stay soft-deleted only (Requirement 3 criterion 8).
**Archived Cards and the Card's Board**
7. [COL-07] WHEN a Card is archived, THE Backend SHALL set `cards.column_id` to null and `archived_at` in the same transaction, and SHALL record the Column the Card left in the `card.archived` ActivityLog metadata (`from_column`, a name, no id needed). THE migration SHALL make `cards.column_id` nullable, set it to null for every already archived Card, and add `cards.board_id` (not null, indexed, foreign key to `boards.id`) backfilled from the Card's Column before it is nulled (Open Question 53). A Card keeps one `board_id` for its life; a Card never moves between Boards.
8. [COL-08] THE Backend SHALL keep the `completed_at` invariant of THR-03 for every Card that has a Column: not null exactly when that Column is the Done_Column, and SHALL amend it for archiving (Open Question 57): a Card in the Done_Column cannot be archived (COL-14), so a Card archived from V17 on never has a `completed_at`, and an already archived Card that has one from before V17 keeps it (throughput still counts it, THR-06); restoring (VIEW-07) treats the Card as entering its new Column, clearing `completed_at` or setting it to now when that Column is the Done_Column. THE invariant SHALL hold for every Column change, including a reorder, a rename, and the delete of an emptied Column.
9. [COL-09] THE Backend SHALL treat a Card with a null `column_id` as outside every board view except Archived: it is excluded from `card_count`, `done_count`, and `overdue_count`, from the Board payload's Columns, from search, from Overdue_Card, and from the analytics of Requirement 10, and it SHALL NOT be movable (HTTP 409 `CARD_ARCHIVED`).
**The Done_Column is locked**
10. [COL-10] IF a request renames the Done_Column, or renames any other Column to `Done` in any letter case, THEN THE Backend SHALL return HTTP 409 with the code `COLUMN_LOCKED`. IF a request deletes the Done_Column, THEN THE Backend SHALL return HTTP 409 `COLUMN_LOCKED`. A request that creates a Column named `Done` in any letter case SHALL receive HTTP 409 `COLUMN_LOCKED`, because every Board already has one. THE Done_Column MAY be reordered. THE Frontend SHALL show the Done_Column's rename and delete controls disabled with the tooltip "The Done column is locked", and SHALL NOT offer to delete it.
**Frontend**
11. [COL-11] THE Frontend SHALL show, to the Board_Owner, a Manager, and an Admin only, at the end of the Column row an "Add column" control and, on each Column header, a menu (`BaseMenu`) with Rename, Move left, Move right, and Delete; every other user sees none of them (the absence of the controls follows the permission, and the Backend still returns 403). Renaming SHALL save on Enter or blur with the V12 auto-save status (Requirement 25). A reorder SHALL update the order at once and reconcile with the response.
12. [COL-12] EVERY Column create and delete SHALL go through ConfirmDialog (FIX-07, Requirement 45). A rename and a reorder SHALL NOT.
13. [COL-13] THE Column header SHALL stay within the Design_System: no new radius, colour, or size; the "Add column" tile uses the Column recipe of Requirement 38 criterion 18 (`--surface-sunken`) at the Column width token. A Board with up to 12 Columns SHALL scroll sideways inside the board area and never widen the page (Requirement 14 criterion 18).
14. [COL-14] IF a Card in the Done_Column is archived (the archive route of Requirement 4 criterion 6), THEN THE Backend SHALL return HTTP 409 with the code `CARD_IN_DONE` and change nothing (Open Question 57, resolved by the owner); a Card must leave `Done` by a move before it can be archived. THE Frontend SHALL show Archive disabled with the tooltip "Move the card out of Done to archive it" in the Card modal footer for a Card in `Done`. THE bulk or Column-level paths SHALL NOT archive a Done Card either.
### Requirement 50: Board Views and Due Badges
**User Story:** As a Board member, I want to read a Board's Cards as a list, on a calendar, or as an archive, and see which Cards are late or due soon, so that I can plan without opening each Card.
The Board, List, Calendar, and Archived pages share the Board_Toolbar, the filters of Requirement 12, and the Card modal (`?card={id}`). They read the Cards through the existing list endpoint; the only new endpoint is the restore action. References: `01-board-desktop.png` for the toolbar; the List, Calendar, and Archived pages have no reference image and use the Component_Recipes (Open Question 63).
#### Acceptance Criteria
**List view**
1. [VIEW-01] THE Frontend SHALL provide `/app/b/{slug}/list` showing the Board's Cards (not archived, not soft-deleted) grouped by Column in Column order, one table section per Column with a header (Column name, count) and one row per Card: title, assignee (name and avatar), priority badge, category pill, and due date with its due badge. THE view SHALL apply the same search and filters as the Board view (Requirement 12) and the same query string, and a selection of a row SHALL open the Card modal. A Column with no Card matching shows "No cards".
2. [VIEW-02] WHILE the viewport is below 960 pixels, THE List rows SHALL stack as cards with the same fields, with no horizontal scroll between 360 and 414 pixels, and each row's hit area SHALL be at least 44 pixels high.
**Calendar view**
3. [VIEW-03] THE Frontend SHALL provide `/app/b/{slug}/calendar`: a month grid (Monday first, matching the throughput week of THR-05) with each Card on its `end_date`, the month and year as a heading, "Previous month" and "Next month" controls and a "Today" control, and the same search and filters. A Card without an `end_date` SHALL NOT be shown. A day with more Cards than fit shows the first ones and a "+N more" control that opens that day's Cards in a `BasePopover`. A selection of a Card SHALL open the Card modal; the Calendar SHALL NOT support drag-and-drop in V17. THE grid SHALL open on the month of the browser's current date and mark that date (a known limit: near midnight the server's `APP_TIMEZONE` date may differ).
4. [VIEW-04] WHILE the viewport is below 960 pixels, THE Calendar SHALL show the month grid with Cards as count dots and the selected day's Cards as a list below it, with no horizontal scroll between 360 and 414 pixels.
**Archived Cards**
5. [VIEW-05] THE Frontend SHALL provide `/app/b/{slug}/archived` showing the Board's archived Cards (Cards with `archived_at`, not soft-deleted) as rows with title, priority, category, archive date (`archived_at`), and a Restore action for a viewer who may archive (Requirement 4 criterion 6). THE Board toolbar SHALL link to it with an "Archived" control that shows the count. THE Backend SHALL return them from `GET /api/boards/{id}/cards?archived=true` (same access as the Board's Card list; the default stays `archived=false`).
6. [VIEW-06] THE Backend SHALL provide `POST /api/cards/{id}/restore`, for a Card_Creator with Board_Staff_Access (the rule of archiving), returning the Card. IF the Card is not archived, THEN it SHALL return HTTP 409 `CARD_NOT_ARCHIVED`. (If an archive-reversal route already exists, the task keeps that one route and documents it, not two.)
7. [VIEW-07] WHEN a Card is restored, THE Backend SHALL clear `archived_at`, set `column_id` to the Board's first Column by `order` (OQ47), place the Card at the end of that Column (`max_order + 1`, Requirement 6 ordering rules), apply COL-08 to `completed_at`, write one `card.restored` ActivityLog row in the same transaction, and notify nobody. THE Frontend SHALL ask no confirmation for Restore (it is not a create or a delete) and SHALL show "Card restored to <Column name>".
**Due badges**
8. [VIEW-08] THE Backend SHALL add a read-only `due_state` to every Card payload (list, detail, create, update, and the shared card): `overdue` when `end_date` is before today, `due_tomorrow` when `end_date` is tomorrow, and null otherwise, with "today" and "tomorrow" taken in `APP_TIMEZONE`, and always null for a Card in the Done_Column or without `end_date`. A posted `due_state` SHALL be HTTP 400. THE rule SHALL be one function, `due_state(end_date, column_name, today)`, used by the schema, My Tasks, and the Dashboard, so the three agree with the Overdue_Card definition of Requirement 10 (Property 79).
9. [VIEW-09] THE Frontend SHALL show a due badge on every Card tile, List row, and Calendar item from `due_state`: "Overdue" on the `danger` tone and "Due tomorrow" on the `warning` tone (`BaseBadge`, Component_Recipes), beside the date. A Card in Done shows none. THE badge SHALL carry text, not colour alone, and the existing "Overdue" red date chip of the Card modal (CardAttributes) SHALL read the same field. THE Frontend SHALL never compute the state from the browser date.
10. [VIEW-10] THE Backend SHALL keep a constant number of queries for the list endpoint with `archived=true` and with the default (Requirement 13, `selectinload` rules), and SHALL add the `board_id` index (COL-07) so the Archived list reads by Board directly.
