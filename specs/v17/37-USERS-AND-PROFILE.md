# Users and Profile, V17 (draft)
### Requirement 53: Users, Active, and Availability
**User Story:** As an Admin, I want to deactivate an account or mark a person unavailable instead of deleting them, so that history and assignments stay intact and work is never orphaned.
This requirement supersedes the Admin user delete (there is none in the specs of Requirement 1; the task removes any route or button that exists), amends Requirement 1 (sign-in) and Requirement 4 (assignee), and keeps Decision B. Reference: `design/reference/v2/08-user-management-desktop.png` and `08-user-management-mobile.png` for the table frame; the table layout itself is built from the Component_Recipes (Open Question 63).
#### Acceptance Criteria
**Data**
1. [ADM-01] THE Backend SHALL add `users.is_active` (boolean, not null, default true) and `users.is_available` (boolean, not null, default true) in the migration of Requirement 59 (migration 3), which sets both to true for every existing user and drops both on downgrade. THE `user` payload (login, register, `GET /api/auth/me`, `GET /api/users`) SHALL carry `is_active` and `is_available`; a payload for another signed-in viewer (comments, members, candidates, assignees) SHALL carry neither flag except `assignee_is_active` and `assignee_is_available` on a Card (criterion 9).
**Admin screen**
2. [ADM-02] THE Frontend SHALL provide `/app/users` (Admin only; any other role is redirected to `/app/boards`; the Sidebar item is shown to an Admin only) as a table with the columns Name (avatar, full name, username), Email, Role (a `BaseCombobox`), Active (a switch), Available (a switch), and Update (a button), one row per user, and a "New user" button above the table. WHILE the viewport is below 960 pixels, rows SHALL stack as cards with the same fields, 44 pixel controls, and no horizontal scroll between 360 and 414 pixels. THE page SHALL keep the search of the V16 Admin users screen (SCR-17) and load users from `GET /api/users`. The document title SHALL be `RevoBoard | Users`. THE Email is shown here because the Admin may see it (Requirement 1 criteria on Admin users).
3. [ADM-03] THERE SHALL be no user delete: THE Backend SHALL NOT expose `DELETE /api/users/{id}` (a call receives HTTP 405), and THE Frontend SHALL show no delete control. THE task SHALL remove the route and the control if they exist.
4. [ADM-04] WHEN an Admin changes a role, Active, or Available switch in a row, THE Frontend SHALL stage the change in that row and enable the row's Update button; WHEN the Admin presses Update, THE Frontend SHALL open a ConfirmDialog naming the user and listing each staged change ("Role: Member to Supervisor", "Active: on to off", "Available: on to off"), and on confirm SHALL send one `PATCH /api/users/{id}` with only the changed fields and update the row from the response (Open Question 62). Cancel SHALL keep the staged values. The "New user" button SHALL open a form modal (full name, username, email, password, role) and the submit SHALL open a ConfirmDialog ("Create user “ada”?") before `POST /api/users`.
**Deactivation rules**
5. [ADM-05] IF an Admin sets `is_active` to false for a user who has Open_Cards assigned, or who owns a Board that has Open_Cards (any assignee), THEN THE Backend SHALL return HTTP 409 with the code `USER_HAS_OPEN_WORK` and `error.details` of `{ "cards": [ { "id", "title", "board_id", "board_slug", "board_name" } ], "boards": [ { "id", "slug", "name", "open_card_count" } ], "cards_total", "boards_total" }`, listing at most 50 of each (the totals are exact), and SHALL change nothing. Cards in the Done_Column, archived Cards, and soft-deleted Cards SHALL NOT block. THE Frontend SHALL show the lists in a modal with a link to each Board (`/app/b/{slug}`) and each Card (`/app/b/{slug}?card={id}`) and the text "Reassign or finish this work first." (Property 74).
6. [ADM-06] IF an Admin sets `is_active` to false on their own account, THEN THE Backend SHALL return HTTP 409 `CANNOT_DEACTIVATE_SELF` (Open Question 59). THE Backend SHALL allow `is_active` and `is_available` to be set by an Admin only; a `PATCH /api/users/{id}` or `PATCH /api/auth/me` that sends `is_active` from a non-Admin SHALL receive HTTP 403, and a non-Admin's `is_available` change is allowed on their own account only (ADM-10).
7. [ADM-07] WHEN a user becomes inactive, THE Backend SHALL end every session of that user at once (Open Question 60): every authenticated request reads `is_active` from the user row and, when it is false, SHALL return HTTP 403 with the code `ACCOUNT_DISABLED` and the message "This account is disabled"; no revocation list is added. THE Frontend SHALL treat `ACCOUNT_DISABLED` on any call like a lost session: remove the Session_Cookie and go to `/app/session-expired`. AN inactive user SHALL NOT be able to sign in: `POST /api/auth/login` with the right password SHALL return HTTP 403 `ACCOUNT_DISABLED`, and with a wrong password the usual 401 (so the response never says whether a disabled account exists), and the failure still counts for the rate limiter (Requirement 20). WHEN both `is_active` is false and the email is not verified, `ACCOUNT_DISABLED` wins.
**Pickers and markers**
8. [ADM-08] THE Backend SHALL list only users who are both active and available in the member picker (`GET /api/boards/{id}/candidates`) and the assignee picker (`GET /api/boards/{id}/members?assignable=true`; the Frontend's assignee popover SHALL send it), and SHALL refuse with HTTP 400 `VALIDATION_ERROR` (`details.assignee_id` or `details.user_id`) an assignment or a direct `POST /api/boards/{id}/members` for a user who is not (Property 73). THE Members view SHALL still list every member of the Board, with an "Inactive" or "Unavailable" tag beside such a person. A Join_Request approval SHALL NOT be blocked by the flags.
9. [ADM-09] A Card in the Done_Column SHALL keep its assignee after the assignee is deactivated (nothing clears it). THE Card payload SHALL carry `assignee_is_active` and `assignee_is_available` beside `assignee_name` (the batched name lookup, no extra query per row; no Email), and `BaseAvatar` SHALL show an "Inactive" marker (a muted ring and the text in its tooltip and `aria-label`) when the assignee is inactive and an "Unavailable" marker when the assignee is unavailable; where both hold, "Inactive" wins. THE Shared_View card carries neither flag.
10. [ADM-10] AN Admin SHALL be able to set both toggles of any user (ADM-04), and a user SHALL be able to set their own `is_available` through `PATCH /api/auth/me` (PRF-04). EVERY toggle change SHALL go through ConfirmDialog (ADM-04 and PRF-04). Making a user unavailable SHALL NOT change their open Cards or sessions.
### Requirement 54: Profile
**User Story:** As a signed-in user, I want a profile page where I manage who I am, how I sign in, and what reaches me, so that my account stays correct and secure.
This requirement supersedes Requirement 29 and Decision AF (two-column layout), PROF-01 (username and email read-only), and PROF-04 (the `PATCH /api/auth/me` body is limited to `full_name`) of Requirement 19 (Decision BG). The page has no reference image; it is drawn from the Component_Recipes and checked in the owner's review (Open Question 63).
#### Acceptance Criteria
**Layout**
1. [PRF-01] THE Frontend SHALL draw `/app/profile` like a social profile page: a cover band (a `--gradient-brand` band of the `card` radius role across the top of the frame), a large avatar (the `size-icon-lg` family or a new `--size-avatar-xl` token) overlapping the lower edge of the band, then the full name (`text-title`) and the username (`--ink-muted`, prefixed with `@`), then a tab list with About, Security, and Notifications (`role="tablist"`, arrow-key navigation, `aria-selected`). THE active tab SHALL be kept in the query (`?tab=about|security|notifications`, default About). THE tab primitive is a new `BaseTabs` in `components/shared/` over the shadcn/ui `Tabs` (the dependency `@radix-ui/react-tabs` is recorded in the design). THE document title SHALL be `RevoBoard | Profile`. THE page SHALL fit 360 to 1280 pixels, the cover band and avatar scaling with token sizes and no horizontal scroll.
**About**
2. [PRF-02] THE About tab SHALL edit: full name; username, with the live availability check (Requirement 1, the debounced `GET /api/auth/availability`, the same format rules 3 to 30 of `a-z 0-9 _ .`); email; and the avatar (choose, preview, upload, remove, as Requirement 19, with the remove asking through ConfirmDialog). THE user saves changed fields with one Save button that is disabled until a field changed and valid; a username or full name change SHALL be a `PATCH /api/auth/me` with only the changed keys. A username that is taken SHALL show the field error "Username is taken" from `details.username`. THE signed-in user's own Email MAY be shown here (it is their own).
3. [PRF-03] WHEN the user changes the email, THE Backend SHALL NOT replace `users.email`: it SHALL store the new address (lower-cased, validated by Requirement 1 criterion 48, not equal to any user's `email` or any other user's `pending_email`) in `users.pending_email`, create an Email_Token of purpose `change_email` (Requirement 59), and send a confirmation link to the NEW address after the commit. The old email SHALL stay the sign-in and notification address until the link is confirmed. THE response SHALL return the `user` with `pending_email`, and HTTP 409 `CONFLICT` with `details.email` when the address is taken. THE About tab SHALL show "Waiting for confirmation: <pending email>" with a "Resend link" action (`POST /api/auth/me/email/resend`, rate limited under the scope of Requirement 59) and a "Cancel change" action (`DELETE /api/auth/me/email/pending`, which clears `pending_email` and invalidates its tokens; asked through ConfirmDialog). WHEN the link is confirmed (`POST /api/auth/verify`), THE Backend SHALL replace `email` with `pending_email`, clear `pending_email`, mark the token used, and fail with HTTP 409 `CONFLICT` if the address was taken in the meantime. A second change request before confirmation SHALL replace the pending address and invalidate the earlier tokens. `pending_email` SHALL be visible to its owner only and SHALL never appear in another user's payload, an activity row, or a notification.
4. [PRF-04] THE About tab SHALL show an "Available for work" switch bound to `users.is_available`; changing it SHALL open a ConfirmDialog and, on confirm, send `PATCH /api/auth/me { "is_available" }`. A user SHALL NOT be able to change their own `is_active` (ADM-06).
**Security**
5. [PRF-05] THE Security tab SHALL hold the change-password form: current password (required), new password (at least 8 characters, Requirement 1), and a confirmation field that must match (client check only). THE Backend SHALL require `current_password` on `POST /api/auth/change-password` and return HTTP 400 `VALIDATION_ERROR` (never 401) for a wrong one, with the rate limit of Requirement 20 (scope `change_password`). WHEN the password is changed, THE Backend SHALL, after the commit, send the email "Your password was changed" to the account's email (the confirmed `email`, not `pending_email`); a failed send SHALL be logged and SHALL NOT fail the request (ACT-09). THE email SHALL carry the time of the change and no password or token. Other sessions stay valid (exclusion 8).
**Notifications**
6. [PRF-06] THE Notifications tab SHALL show one switch per type of Requirement 57, with its label and a one-line description, loaded from `GET /api/me/notification-preferences`. EACH switch SHALL save at once through `PUT /api/me/notification-preferences` with the V12 field status (Saving, Saved, or an error with Retry in an `aria-live="polite"` region), roll back on failure, and need no ConfirmDialog (a preference is neither a create nor a delete). The tab SHALL say "These control in-app notifications only."
**Rules that stay**
7. [PRF-07] THE avatar rules (Requirement 19, AVT-01 to AVT-16: PNG, JPEG, or WebP up to 2 MB, signed URL, initials fallback) and the `BaseAvatar` use SHALL stay unchanged. THE User_Menu keeps Profile above Log out (HDR-02 to HDR-05).
8. [PRF-08] THE Backend SHALL validate `username` on change by Requirement 1 criterion 47 and its uniqueness case-insensitively, and SHALL keep PROF-08: a successful profile change (name, username, email request, availability) or password change writes one Activity_Log row (`user.profile_updated` or `user.password_changed`, target type `user`) in the same transaction, with no password, hash, Token, or email address in `metadata`. A username change takes effect for sign-in at once.
9. [PRF-09] THE `PATCH /api/auth/me` body SHALL accept `full_name`, `username`, `email`, and `is_available` only; any other key (including `role`, `is_active`, `pending_email`, `email_verified_at`) SHALL be HTTP 400 `VALIDATION_ERROR`.
10. [PRF-10] THE availability check for the profile's username SHALL exclude the caller's own current username, so keeping the name is "available"; THE check stays rate limited (Requirement 20).
