# Verification, V17 (draft)
This file is the V17 test plan. It extends Requirement 15 and Requirement 44 and is written with the implementation tasks of group 39. It is not a numbered requirement: the brief assigns Requirements 45 to 59 to features, and the test criteria below carry their own IDs `[V17-Txx]`. Every criterion is written as an EARS acceptance criterion. Backend tests use `pytest` (SQLite for logic, PostgreSQL where the existing migration tests use it) and `hypothesis`; frontend tests use `vitest` and `fast-check`; end-to-end tests use Playwright (Requirement 15 and `tech.md`: read-only against the deployed URL, no `waitForTimeout`).
## Test plan
### Unit tests
1. [V17-T01] THE Backend SHALL include unit tests, against fake repositories, for: `slugify` (the examples of SLUG-02 and the empty and symbol-only names); the suffix rule (`-2` is the lowest free); `due_state` (overdue, tomorrow, today, null date, Done); the My Tasks grouping function (every boundary: yesterday, today, tomorrow, Sunday, Monday, no date); the dashboard on-time rule (same day, one day late, no `end_date`, a `completed_at` near midnight in `APP_TIMEZONE`); the completion stamp with archive and restore (COL-08); the column service (Board_Owner, Manager, and Admin; a BoardMember Supervisor and a Member refused, `COLUMN_NOT_EMPTY` with its count, `COLUMN_LOCKED` for rename, delete, and create of `Done` in any case, duplicate name 409, reorder renumbering); the user service (`USER_HAS_OPEN_WORK` with its lists and the 50 cap, `CANNOT_DEACTIVATE_SELF`, Done and archived Cards do not block); the notification producers (comment, move, archive, delete, Subtask create, change, delete; no row for the actor, for a disabled type, for an inactive user, or for an unassigned Card); the preference service (default enabled, upsert, unknown and duplicate types); the email-token service (create, hash, expire, single use, replaced on resend, `TOKEN_INVALID` versus `TOKEN_EXPIRED`); and the mail module (console backend, in-memory outbox, missing SMTP settings fail at startup, a failed send is logged and swallowed).
2. [V17-T02] THE Frontend SHALL include unit and component tests for: `greeting(date, fullName)` at 00:00, 11:59, 12:00, 17:59, 18:00, and 23:59 and with an empty name; `lib/routes.ts` helpers and the scan that no component writes a route string by hand (PATH-10); `navItems` visibility for each role, with and without an open Board, and that no id is in both lists (NAV-05); the Sidebar toggle (default expanded, safe read of a bad `localStorage` value, tooltip only on hover and focus, `aria-expanded`); the Top_Menu items, active state, and Side_Panel views; `ConfirmDialog` (names the item, Escape, Cancel, focus return, busy state, error kept) and, per action in FIX-07, one request after confirm and none before (FIX-11); `BaseCombobox` and `BaseMenu` hover and keyboard highlight (FIX-05); form error clearing and submit-time validation of every field (FIX-03, FIX-04); the 404 page content and that it shows no slug (SLUG-11, SLUG-13); the Column menu per role and the locked `Done` tooltip; List, Calendar (month grid, no `end_date` hidden, "+N more"), and Archived rows; the due badge from `due_state` (never from the browser date); the Users table (staged changes, the Update ConfirmDialog, the `USER_HAS_OPEN_WORK` modal with links, no delete control); the Profile tabs, email-pending state, and password form; the Share_Modal sections per role (owner, Manager, Admin) and that the owner sees no Public link section; the Card modal chip row (status chip read-only); the Notifications switches (save at once, roll back on failure); and the verify page states (sent, confirmed, `TOKEN_EXPIRED`, `TOKEN_INVALID`, 429 countdown).
3. [V17-T03] THE Frontend SHALL keep every check of `frontend/tests/styling.test.ts` (no hex, no arbitrary value, no raw `<button>`, no numeric `z-`, `duration-`, `opacity-`) and SHALL extend it to the new files (`components/shell/Sidebar.tsx`, `TopMenu.tsx`, `ConfirmDialog.tsx`, `BaseTabs.tsx`, the List, Calendar, Archived, My Tasks, Users, Profile, Share, and 404 components) so a magic number fails the build. THE new tokens (`--sidebar-w`, `--sidebar-w-collapsed`, `--size-avatar-xl`) SHALL be covered by the token test and the contrast test of V16-T02.
### Property tests (Properties 69 to 80)
4. [V17-T04] THE Backend SHALL include `hypothesis` property tests for Properties 69, 70, 71, 72, 73, 74, 75, 76, 77, 78, 79, and 80 (see `design.md`), each a function of generated Boards, Columns, Cards, users, preferences, and dates, with at least 100 examples and a fixed seed in CI. THE Frontend SHALL include `fast-check` tests for the pure parts: `greeting` (Property 80 does not apply), the My Tasks grouping mirror, the route helpers round trip, and the Sidebar state parser, each with at least 100 runs.
### Integration tests
5. [V17-T05] THE Backend SHALL include API tests (the Flask test client, the Envelope on every path) for: `GET /api/boards/slug/{slug}` (200, 401, 403, 404, an old slug after rename, an invalid character); the Column endpoints (every role, 409 codes, activity rows, `Done` reorder); archive then restore (null `column_id`, `board_id` kept, first Column, `completed_at`, `card.restored` row); `GET /api/boards/{id}/cards?archived=true`; `due_state` on every Card payload and its rejection in a body; `GET /api/analytics/dashboard` (roles, `board` and `member` and range validation, the 182 day limit, the table of DASH-12, constant query count over 10 and 200 Cards using the existing query counter); `GET /api/me/cards`; the user endpoints (`PATCH` with `is_active`, 409 codes, `ACCOUNT_DISABLED` on login and on an existing Token, no `DELETE` route 405); the assignee and candidate pickers; the profile routes (username change, email change with `pending_email`, confirm, cancel, resend, conflict on confirm, password change with an email in the outbox); the preference routes and the producers inside one transaction; register with `token: null`, verify, resend with the same answer for known and unknown addresses, and the 429; and login order (wrong password 401, then `ACCOUNT_DISABLED`, then `ACCOUNT_NOT_ACTIVATED`).
6. [V17-T06] THE Backend SHALL include migration tests on PostgreSQL, one per migration (the existing `test_migrations.py` pattern): upgrade on data, downgrade, and upgrade again. THE tests SHALL assert: migration 1 gives every Board a distinct slug, the earliest Board keeps the plain slug, and downgrade drops the column; migration 2 backfills `board_id` for every Card, nulls `column_id` only for archived Cards, and the downgrade puts each archived Card back in its Board's first Column before it restores NOT NULL and drops `board_id`; migration 3 sets `is_active`, `is_available`, and `email_verified_at` for every existing user and creates `email_tokens`; migration 4 creates `notification_preferences`, extends the type values, adds `action`, and replaces `uq_notifications_card` with the narrower partial index and restores the old one on downgrade, with no row lost. THE migrations SHALL leave production data untouched except by their stated backfills (Property 61).
7. [V17-T07] THE Backend SHALL include a test that `flask notify-due` called twice on one date inserts nothing the second time, honours preferences, skips Done, archived, soft-deleted, unassigned, and inactive-assignee Cards, uses `APP_TIMEZONE` at the date boundary (a run at 23:50 and at 00:05 local), and a test of the advisory lock on PostgreSQL.
8. [V17-T08] THE System SHALL pass `pytest`, `tsc --noEmit`, `vitest run`, and `next build` unchanged in command, with `backend/openapi.json` current (`test_committed_openapi_json_is_current`) and `backend/API.md` regenerated, at the end of every phase of group 39.
9. [V17-T09] THE deploy smoke test (`deploy/smoke.mjs`) SHALL check the PATH-11 list against the throwaway stack in CI: `/` returns the Landing_Page with "RevoBoard", `/app/login` is 200, `/app/api/health` is 200, `/api/health` is 404, `/boards` is 308 to `/app/boards`, `/app/xyz` is 404 with the Not_Found_Page, the `X-Robots-Tag: noindex` header is on `/app/login`, and `robots.txt` and `sitemap.xml` name `/` only.
### Playwright at four widths
10. [V17-T10] THE Frontend SHALL include a Playwright project (the repository has none yet, task 39.50) that, at 360, 414, 960, and 1280 pixels wide, opens each of these pages and asserts that the document has no horizontal scroll (`scrollWidth <= clientWidth`), that every interactive control below 960 pixels has a hit area of at least 44 pixels, and that nothing overlaps or is cut off: the Landing_Page, login, register, the verify page, the Not_Found_Page, Boards, a Board, List, Calendar, Archived, the Card modal, the Share_Modal, the Members, Categories, Activity, and Inbox views of the Side_Panel, the Dashboard, My Tasks, the Users page, and the Profile (each tab). THE tests SHALL use `expect(locator)` waits and no `waitForTimeout`, SHALL be read-only against a seeded environment, and SHALL leave the invite and join flow to the manual checklist (Requirement 15).
11. [V17-T11] THE Playwright suite SHALL also check, at 1280 pixels, the computed height, radius, and fill of the new shared components against the token values (the method of V16-T16): `ConfirmDialog`, `BaseTabs`, the Sidebar in both states, the Top_Menu, the due badges, and the Not_Found_Page buttons; and, at 360 pixels, the Nav_Drawer focus trap, Escape, and focus return.
12. [V17-T12] THE Playwright suite SHALL save a screenshot of each page of V17-T10 at 1440 by 900 and 390 by 844 pixels to a git-ignored folder for the owner's review; THE suite SHALL not compare pixels.
## Owner's visual review checklist
13. [V17-T13] BEFORE group 39 is ticked complete, THE implementer SHALL put each built screen beside its reference at 1440 and 390 pixels for the owner and record the owner's decision on every difference in `specs/CHANGELOG.md` (the method of V16-T15). A difference the owner accepts is written down; one the owner rejects becomes a task. The owner checks:
   - [ ] Login and register: transparent logo, same canvas as Boards, errors clear while typing, every error shows on submit (`05-auth-*`).
   - [ ] Sidebar expanded and collapsed, the Top_Menu on a Board, the bell and Inbox panel, the Nav_Drawer below 960 pixels (`01-board-*`, `11-inbox-*`).
   - [ ] Members, Categories, and Activity panels, with the spacing under the header (`09-categories-*`, `13-activity-*`).
   - [ ] The 404 page at 360 and 1280 pixels (no reference; judged on brand and clarity).
   - [ ] Board with Column menu, locked Done, Add column, List, Calendar, Archived (no reference for the last three).
   - [ ] Due badges on a Card tile, a List row, and a Calendar item.
   - [ ] Dashboard: greeting, filters, the seven widgets, empty and loading states (`03-dashboard-*`).
   - [ ] My Tasks groups (no reference).
   - [ ] Users table and its stacked cards, the deactivation modal, the markers on an avatar (`08-user-management-*`).
   - [ ] Profile: cover band, large avatar, About, Security, Notifications, the pending-email state (no reference).
   - [ ] Share modal for an owner, a Manager, and an Admin (`06-invite-public-link-*`).
   - [ ] Card modal and its chip row (`04-card-modal-*`).
   - [ ] ConfirmDialog for a create and for a delete.
   - [ ] The verification email, the email-change email, and the password-changed email as received in a real inbox.
14. [V17-T14] THE implementer SHALL ask the owner before any action on the server (the deploy, the cron or loop install, the nginx change, the Gmail app password), and SHALL record in `deploy/README.md` how to roll the topology back to the V16 layout.
